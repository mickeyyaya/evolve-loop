## Summary
The `go-run-exit-code` unsatisfiable lint now follows an exit code held in a variable. It flags `code := ee.ExitCode(); if code != 3` (and the `ProcessState`, `var` and `=` forms) after a `go run` command, and `_, _, code, _ := acsassert.SubprocessOutput("go", "run", ...); code != 3`. Reachable codes (0, 1, and 2 when go flags precede the package) and built-binary exit codes stay unflagged.

## Rationale
`go run` reports any non-zero exit of the program it runs as 1, so a predicate comparing that exit code to 3 is red on every tree. The rule already proved this for a direct `ExitCode()` call; the copied-variable and `SubprocessOutput` shapes are the common ways predicates are actually written, so the lint missed them. Adding one binding kind to the existing scoped name table reuses all of its shadowing, rebinding and closure-boundary semantics instead of adding a second tracker.

## Changed Areas

## Design Decisions
`acsassert.SubprocessOutput` returns `(stdout, stderr, code, err)`, so it is a source of an exit code, not a command: it binds only the third name of a four-name assignment. Excluding it from `goRunCommand` changes nothing for compiling code (its first result is a string and has no `ProcessState`). A copied exit code carries the `goFlagsGiven` fact of its command, so the 2-is-reachable rule still applies.

## Limitations
An exit code returned from a helper function, held in a struct field, or read inside a closure from an outer scope is still not followed.
