# Build Explanation — Cycle 1781

## Build Binding
- Cycle: 1781
- Base SHA: a24c24c937acdb2f1bae3efde6bc7bc616f402c7

## Summary
Two lane tasks ship together. First, the claim path now refuses an inbox item whose declared dependency has not landed, and it names the blocker. This is the same `PendingDispatchability` rule the lane menu already uses. Second, a failed lane's continuation stamp no longer writes the operator's absolute home path into a tracked inbox item. The continuation resolver expands `~` again, so the next builder can still open the findings.

## Rationale
The claim facade (`inboxmover.go`), the mover (`inboxmover/lifecycle/`) and core's findings reader are protected surfaces, so a lane cannot edit them. Each fix therefore sits at the nearest seam a lane can edit:
- The claim floor is a new `ClaimDispatchable` in `claim_pending.go`. Both production claim callers go through it: the host claimer (`ClaimPending`, wired in `cmd_cycle.go` as `hostInboxClaimer`) and `evolve inbox-mover claim`.
- Redaction happens in `continuation.ReadManifest`. That function is the only source the protected stamp writer (`lifecycle/release.go` `readStamp`) reads from.
- Expansion happens in `inboxmover.resolveClaim`. Core opens the value it returns without changing it.

## Changed Areas
- `go/internal/inboxmover/claim_pending.go` — adds `ErrWaitingOnDependency` and `ClaimDispatchable`. The new check runs only on a root-pending item: if its deps are not dispatchable, it refuses the claim, prints the blocker (for example "deps unmet: needs dep-a"), and leaves the item pending. `ClaimPending` now routes through this check and treats the refusal like a console-routed one: it leaves the item for the deliverable effects gate.
- `go/cmd/evolve/cmd_inbox_mover.go` — `claim` now calls `ClaimDispatchable` and exits 4 on a dependency-waiting refusal. The error→exit-code mapping moves into `claimExitCode`, which keeps `runInboxMover` within its function-size ratchet allowance (78 lines).
- `go/internal/continuation/continuation.go` — `ReadManifest` returns the manifest after `RedactHostPaths`. Its other callers (defect ledger, ship manifest) read only `Cycle`, so they see no change.
- `go/internal/continuation/registry.go` — adds `ExpandHostPaths`, the inverse of `RedactHostPaths`. It expands `~/` using the current home directory and passes every other path through unchanged.
- `go/internal/inboxmover/continuation_resolve.go` — `resolveClaim` expands the claimed item's stamp before returning it, so `findings_path` can be opened as given.
- `go/internal/inboxmover/claim_pending_test.go` — unit test: a waiting item is refused, the blocker is named, and the item stays at the root; an item whose dependency has landed is claimed.
- `go/internal/continuation/registry_operator_test.go` — unit tests: expanding a redacted stamp gives back the original, `ExpandHostPaths` leaves non-tilde paths alone, and `ReadManifest` redacts.
- `go/acs/cycle1781/predicates_test.go` — the TDD phase's cycle predicates (not written by the builder). They cover claim refusal, no over-blocking, redaction, the absolute registry, and resolver expansion.
- `.evolve/evals/claim-floor-refuses-waiting-items.md` — the TDD phase's permanent eval for the claim floor.
- `.evolve/evals/pending-continuation-stamps-carry-host-paths.md` — the TDD phase's permanent eval for stamp redaction.
- `docs/explain/builds/cycle-1781-01m3s6dk1fp9f248j4w795s9wh.md` — this document.

## Design Decisions
- The floor reuses `ResolveDispatchState` and `PendingDispatchability`, so the menu and the claim cannot disagree.
- The floor applies only when the item is root-pending, so claims of items in any other state keep their existing behavior.
- `ClaimPending` does not return an error for a waiting item. Like the console-routed refusal, it reports the item on stderr and leaves it to the effects gate (`checkInboxClaim`). That gate then fails a committed-but-unclaimed item.
- The console line reuses `lifecycle.LegacyPrefix`, the single home of the `[inbox-mover] ` prefix (pinned by `TestInboxMoverPrefix_OneHome`).
- The registry keeps absolute paths: `core.registerLaneScopeBinding` writes the in-memory manifest, not a `ReadManifest` result.

## Compatibility
- `evolve inbox-mover claim` keeps exit codes 0–3 and adds exit 4.
- Stamps that already carry absolute paths still resolve, because `ExpandHostPaths` leaves absolute paths unchanged.

## Limitations
- `~` expands against the home directory of the process that resolves it. A stamp redacted on a different host or account resolves to that host's home.
