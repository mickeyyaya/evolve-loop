# Test-case design catalog

This catalog is the implementation contract for the [refactoring design](../../architecture/test-refactoring-design-2026-09-14.md), pinned to `80b348e6`. It groups concrete inputs by behavior and owner; it does not replace the [14,496-test inventory](test-inventory.tsv).

**Evidence labels:** **reproduced** means a temporary experiment demonstrated the defect; **reviewed** means the cited code/test was inspected; **investigate** means the scenario is a proposed gap, not a proven absent test or production failure. Before adding a case, search the owner package and preserve/extend an existing table when equivalent coverage exists. Existing behavior and proposed stronger behavior are deliberately identified separately.

## Case representation and promotion

Use ordinary package-local Go tables for small input variations. Keep independent arrange/act/assert stages and fresh mutable fixtures per row. A table is useful only if it improves readability without hiding the reason each row exists. For larger captured artifacts, use package-local `testdata` with an existing parser and a minimal typed loader; reject malformed cases and duplicate IDs and require at least one selected case. The historical generic regression-manifest design is not evidence that a universal loader is implemented.

For each newly added or consolidated case, attach the following short review record to its change description:

```text
Requirement: stable behavior ID and incident/reference
Owner/tier: package; build constraints; OS/capabilities; CI lane
Given/when/then: input, operation, exact observable and forbidden outcome
Old -> new: complete test/subtest identities and selector consumers
Oracle: independent expectation; known-good and known-bad control
RED: baseline tree, executable test inputs, selected IDs, command, semantic failure
GREEN: candidate tree, same test inputs/selection/environment, success event
Preservation: original cases; block/API comparison; fault sensitivity
Exceptions: skips, invalid/equivalent mutants, platform limitations
```

Pure refactors replace RED/GREEN behavior-change evidence with the original green characterization and isolated fault-sensitivity comparison. New helper/grader behavior still follows strict RED-first TDD. A rename must migrate external `-run` selectors and ACS references before removing the old identity. The current change removes no tests and does not claim these future cases have all been implemented.
