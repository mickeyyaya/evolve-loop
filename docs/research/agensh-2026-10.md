**Terms used throughout:**

- **Worker:** one Agensh agent. It runs its own loop with its own private branch.
- **Board:** the Agensh shared context. It is a log of short typed entries that only grows.
- **Lane:** one of our autonomous build loops. A **wave** is one batch of lanes between two boundaries. A **cycle** is one item from claim to ship or to stop.
- **Cell:** one phase dispatch of a cycle, with its own assignment, its own context index and its own sandbox.
- **Context index:** the per-cell list of entries in layers L0 to L3 that a cell opens on demand ([cell-context-index.md](../architecture/cell-context-index.md)). L2 is the recovery layer and L3 is the knowledge layer.
- **Channel:** one push log of the event protocol, with cursors, retention and a retry schedule.
- **Differential test:** a test that runs a reference program and the candidate program on the same input and compares the two outputs.

## 1. Request

The console asked on 2026-10-26 for a research record of Microsoft Research's open-source Agensh, and of "what evolve-loop can learn from it". The analysis must measure Agensh against our design of record. It must name what conflicts with our invariants, what we can adopt inside the pipeline, and what evidence changes our mind.

## 2. What Agensh is

The answer first: Agensh is a team of coding agents with no central orchestrator. Each worker claims its own sub-task, and the workers coordinate through a git server, a chat server and a shared board. On ProgramBench, more workers gave a higher final test-pass rate, but the paper gives no ablation, no cost and no repeat runs.

### 2.1 The paper and the code

**P2.1** The paper is "Agensh: Scaling Organizational Intelligence to 1,024 Agents" by Zhihao Zhan, Ting Song, Li Dong, Shaohan Huang, Jianxun Lian, Yan Xia and Furu Wei. It is arXiv:2609.26781, v1 of 2026-09-22 ([S1](#8-sources), [S2](#8-sources)).

**P2.2** The code is `microsoft/Agensh` under the MIT license. The repository has the folders `mini-router` and `board-service`. It starts a team on one node with Docker Compose (`scripts/launch_single_node.sh`) and a single-agent baseline (`scripts/launch_single_agent.py`). The loop of each agent is the GitHub Copilot CLI harness ([S3](#8-sources)).

### 2.2 The worker loop

**P2.3** Each worker runs one loop of five steps, with no orchestrator ([S2](#8-sources) §2.1):

1. Gather the context.
2. Claim a sub-task. The worker appends a `CLAIM` entry to the board. A peer settles an overlap of two claims by direct message.
3. Act on the sub-task.
4. Verify the result against the acceptance of the sub-task.
5. Merge to `main`. On a conflict, the worker pulls, resolves and merges again. Then it publishes a `PATCH_SUMMARY` entry and goes back to step 1.

*Implication:* the claim, the split of the work and the merge order are decisions of LLM workers. No deterministic program makes them.

### 2.3 The three components

**P2.4** The shared workspace is a Gitea git server. Each worker has a private branch and opens pull requests ([S2](#8-sources) §2.2, [S3](#8-sources)).

**P2.5** The message interface is a Mattermost server. A task channel message reaches a worker at the start of a loop step. A direct message reaches a worker at the end of each infrastructure tool call ([S2](#8-sources) §2.2).

**P2.6** The shared context is a board of typed entries that only grows. The board design comes from DeLM ([S4](#8-sources), [S5](#8-sources)). The entry types are in the table ([S2](#8-sources) §2.2, App. A).

| Type | Meaning | Limit |
|---|---|---|
| `OBSERVED` | a behavior of the reference that a worker noticed | 100 characters |
| `FACT` | a confirmed finding | 100 characters |
| `FAIL` | a hypothesis that a worker falsified | 100 characters |
| `CLAIM` | work in progress | 100 characters |
| `PATCH_SUMMARY` | `files= \| idea= \| evidence=` | 300 characters |

A longer text goes into a `detail` field, and a peer opens it with `board_unfold`. New entries reach each worker in the result of its next infrastructure tool call, and the prompt of each turn shows the board. `board_read` gives the latest 2,000 entries. `board_grep` searches the full history ([S2](#8-sources) App. A, App. B.2).

*Implication:* the board is the part of Agensh that stops a worker from a retry of a falsified idea. It does not need the chat server to do that.

### 2.4 The runtime

**P2.7** A router listens to Gitea through server-sent events and to Mattermost through a live connection. On a reconnect it fetches the missed messages. Each event goes into a durable queue with a unique id for deduplication. A failed delivery retries with a longer wait each time. After a router restart, the events that did not finish go back into the queue ([S2](#8-sources) App. B.1).

**P2.8** The router sends a "continue working" prompt after 10 minutes of idle time. When a turn adds no board entry, a follow-up prompt asks the worker to publish its findings ([S2](#8-sources) App. B.1, App. C).

**P2.9** At 128 workers, a peer took over the integration of a contribution. At 1,024 workers, peers in the same area took over after a failed try. Some workers acted as integrators: a worker asked several integrators, kept the first valid answer and cancelled the other requests ([S2](#8-sources) §3.2). The paper reports these roles as emergent. No configuration assigns them.

**P2.10** The launch is staggered: one agent each 30 s in the first hour, then one each 3 s. The 1,024-worker runs use 16 nodes with 64 agents each. All agents stop at 6 h after the first start. Reminders at T − 45 min and T − 5 min tell the workers to stop new features and to merge ([S2](#8-sources) App. C).

### 2.5 Verification

**P2.11** A worker verifies its work with a differential test. It runs the reference binary and its own build on the same inputs and compares the outputs. A merge requires the acceptance of the sub-task ([S2](#8-sources) §2.1, App. A).

**P2.12** The grader builds a fresh clone of `main`. It requires a root `compile.sh` that makes `./executable`, and it runs hidden tests with the official ProgramBench evaluation ([S2](#8-sources) App. C, [S6](#8-sources)).

### 2.6 Results

**P2.13** The setup is GPT-5.6-sol at high effort, the Copilot harness, 6 h and no internet access. The token limit is 272,000 input and 128,000 output ([S2](#8-sources), [S3](#8-sources)).

| Benchmark | 1 agent | 8 | 32 | 128 | 1,024 |
|---|---|---|---|---|---|
| Five hardest ProgramBench tasks, mean final pass rate | 19.31% | 20.68% | 26.52% | 28.78% | not run |
| pandoc, final pass rate | 33.89% | not given | not given | 50.94% | 55.06% |
| pandoc, time to pass 30% | not in the first 2 h | 90 min | 60 min | 30 min | not given |

**P2.14** The README also reports pandoc with GPT-6.1-sol: 56.19% with 1 agent and 79.59% with 32 agents ([S3](#8-sources)).

*Implication:* from 128 to 1,024 workers, pandoc gained 4.12 points for 8 times the agents. Most of the gain comes before 128 (synthesis).

### 2.7 Limits of the evidence

**P2.15** The paper reports no ablation. Thus no result says which component (the board, the messages, the claims or the width) gives the gain ([S2](#8-sources)).

**P2.16** The paper reports no cost for each agent and no total token count ([S2](#8-sources)).

**P2.17** Each configuration ran once. The paper gives no repeat runs and no variance ([S2](#8-sources)).

**P2.18** The single-agent baseline gets a different continuation prompt. A stop hook sends "There is always new work...". The team gets an idle prompt about the gap to the reference ([S2](#8-sources) App. C). The two arms thus differ in more than the team size.

**P2.19** The 1,024-worker run is on pandoc only ([S2](#8-sources), [S3](#8-sources)).

**P2.20** The news article of MarkTechPost returned HTTP 403 on 2026-10-26, so we did not read it ([S7](#8-sources)). Two other summaries repeat the same numbers (secondary, [S8](#8-sources), [S9](#8-sources)).

*Implication:* the evidence shows that a large team did better than one agent on these tasks. It does not show that the absence of an orchestrator is the cause.

## 3. Local evidence

**F3.1** ADR-0154 says that the pipeline is the only controller ([ADR-0154](../architecture/adr/0154-the-pipeline-is-the-only-controller-and-each-agent-is-an-isolated-replaceable-worker.md) items 1 to 5):

- I-1: only the bridge launch API starts an LLM binary.
- I-3: an agent cannot start a new LLM CLI process and cannot run an `evolve` dispatch verb. The amendment of 2026-10-26 allows a subagent of the own harness inside the cell. To get another phase agent, the agent writes a dispatch request. The pipeline validates it, the orchestrator judges it, and only the pipeline dispatches.
- I-4: agents communicate only through declared artifacts that the pipeline records and indexes.
- I-5: an agent reads its own cycle, its item lineage and its own CLI files, and nothing else.

*Implication:* each Agensh mechanism that lets one LLM direct another LLM is out. A mechanism that the pipeline carries is a candidate.

**F3.2** ADR-0155 lets an orchestrator agent propose one action from a closed catalog, and the deterministic pipeline disposes (I-12) ([ADR-0155](../architecture/adr/0155-the-loop-heals-itself-inside-its-boundaries-an-agent-proposes-and-the-pipeline-disposes.md) items 8 and 9).
*Implication:* the Agensh takeover of a failed try (P2.9) has a version in our design: a proposal, then a dispatch that Go checks.

**F3.3** ADR-0129 delivers messages through a broker of one cycle. Cross-cycle delivery is impossible by construction ([ADR-0129](../architecture/adr/0129-cycle-scoped-agent-messaging.md) item 3).
*Implication:* a direct message from one lane to another lane has no path, by design.

**F3.4** The cell context index has an L3 knowledge layer. The spec lists the rule rows, the recalled lessons, the docs index and the `evolve code` verbs. An L3 entry is never required and adds no grant ([cell-context-index.md](../architecture/cell-context-index.md) §3, §6 and §10). The item `context-index-knowledge-layer` (CX7b) adds the docs index and the code verbs.
*Implication:* the pipeline already has a read path for knowledge that comes from outside the lineage. A board of findings fits into it as one more L3 kind.

**F3.5** The phase observer already sends an idle nudge. The default is a nudge at 300 s and a stall at 600 s (`go/internal/policy/dispatch.go:61`). The engine sends the nudge once for each phase (`go/internal/observerengine/tick.go:87`), and the default body is "You appear stalled. Summarize your current state, then either continue or finalize your artifact." (`go/internal/phaseobserver/phaseobserver.go:115`).
*Implication:* the idle rung of P2.8 exists. The "no finding this turn" reminder does not.

**F3.6** `evolve wave watch` polls each 5 s (`go/cmd/evolve/cmd_wave.go:27`). The event protocol plan moves it to a view over the `loop` and `cycle` channels ([event-notification-protocol-2026-10](../plans/event-notification-protocol-2026-10.md) §9). The E9 verbs are not started (same plan §16), and the inbox has the item `events-cli-verbs-e9`.
*Implication:* the move from the poll to a push is planned. Agensh adds no new reason to do it.

**F3.7** The channel design already gives these guarantees (plan D7, D17, D18; [event-channels.md](../architecture/event-channels.md) §9, `backoff_s` 10, `max_deliver` 5):

- a durable log, with a cursor for each subscriber;
- at-least-once delivery, with an ack after success;
- the event id as the idempotency key;
- a fixed retry schedule, with a dead letter;
- the redelivery of unacked records after a crash.

*Implication:* the Agensh router (P2.7) and our channels give the same guarantees for local events. The one gap: `ship.landed` is at most once. A stop between the write of the `complete` intent and the emit loses the event, and no retry repeats it ([event-channels.md](../architecture/event-channels.md) §14).

**F3.8** On 2026-10-17, host load caused two Claude REPL boot timeouts (exit 80) at width 4 ([wave-orchestrator.md](../architecture/wave-orchestrator.md) F12.1, F12.2). The recorded cause is the CPU load of the test floors, not a simultaneous launch.
*Implication:* a staggered launch is a cheap guard, but our evidence does not prove that a simultaneous launch causes boot timeouts.

**F3.9** [ADR-0147](../architecture/adr/0147-the-wave-orchestrator-owns-integration-and-decides-when-the-wave-reaches-main.md) (proposed) gives the integration to the wave orchestrator: the order, the compose, the test and the push. The serial landing binds at about 6 lanes, and the default width is 4 ([ADR-0139](../architecture/adr/0139-a-wave-orchestrator-supplies-admits-and-backfills-every-lane.md) item 3, [wave-orchestrator.md](../architecture/wave-orchestrator.md) §12).
*Implication:* the integrator of Agensh is a deterministic program in our design. The limit of about 6 lanes is a limit of the landing throughput, not of conflicts. A width above 6 needs the group commit of [ADR-0134](../architecture/adr/0134-fleet-landings-scale-through-content-keyed-verification-and-group-commit.md) first. An LLM seat for a conflict has value only when, after the group commit, a measured conflict rate asks for it.

**F3.10** The certificate kinds of the audit are a closed set: `test`, `command`, `mutant`, `artifact`, `diff` and `kernel` ([audit-evaluation-contract.md](../architecture/audit-evaluation-contract.md) §2.2). No kind compares a candidate with a reference program.
*Implication:* a port of a tool to a Go verb has no certificate that proves the same behavior on the same inputs.

## 4. What conflicts with our invariants

The answer first: we do not adopt the self-claim, the direct messages or the emergent roles. Each of them is an LLM that directs another LLM.

| Agensh practice | Decision | Reason |
|---|---|---|
| A worker claims its own sub-task (P2.3 step 2) | reject | The supply and admit steps of ADR-0139 are deterministic and admit by cell. A self-claim moves the dispatch decision into an LLM (I-3, F3.1). The sanctioned form of "ask for more work" is a dispatch request (inbox item `isolation-dispatch-request-channel`), and the decision stays with the pipeline. |
| Direct messages settle an overlap of claims (P2.3, P2.5) | reject | The agents of Agensh message across workers. Our messages go through the broker of one cycle, and that path obeys I-4 (ADR-0129 item 7). A message from one lane to another lane has no path by construction (F3.3), so a settlement between lanes is a pipeline decision. |
| A worker asks several integrators and keeps the first answer (P2.9) | reject | One LLM selects and cancels the work of other LLMs. That is control (I-1, I-3). |
| A peer takes over a failed try (P2.9) | adopt in our form, already designed | The orchestrator agent proposes a retry or a reroute, and the pipeline disposes (I-12, F3.2). No change. |
| Each worker merges its own branch to `main` (P2.3 step 5) | reject | Only `evolve ship` commits, and the wave orchestrator owns the order of integration (F3.9). |
| The board is read by each worker directly (P2.6) | adopt only through the pipeline | A direct read of another lane breaks I-5. The pipeline copies vetted entries into the context index of a cell (§6, R1). |

*Synthesis:* the Agensh results do not need these practices to explain them. Without an ablation (P2.15), the width, the board or the differential tests can each explain the gain.

## 5. Adoption options and scores

Each criterion has a score from 1 (weak) to 3 (strong). **Fit** is the fit with I-1 to I-5 with no change to an invariant. **Evidence** is the strength of the proof that the practice helps. **Cost** is 3 for a small change and 1 for a new subsystem. **Gain** is the expected effect on our ship rate or our wasted cycles.

| Id | Option | Fit | Evidence | Cost | Gain | Total | Decision |
|---|---|---|---|---|---|---|---|
| A1 | A typed board of findings that only grows, carried by the pipeline, read through L2 and L3 | 2 | 1 | 1 | 3 (estimate) | 7 | adopt (proposed), R1 |
| A2 | `ship.landed` at least once through an outbox (the restart re-queue of P2.7) | 3 | 2 | 2 | 2 | 9 | adopt (proposed), R2 |
| A3 | A "no finding this turn" reminder before the stall kill | 3 | 1 | 3 | 1 | 8 | adopt (proposed), R3, after R1 |
| A4 | A staggered lane launch | 3 | 1 | 3 | 1 | 8 | adopt (proposed), R4 |
| A5 | A differential certificate kind against a reference | 3 | 2 | 2 | 2 | 9 | adopt (proposed), R5 |
| A6 | An integrator seat for conflicts at high width | 2 | 1 | 1 | 1 | 5 | defer |
| A7 | A durable queue with dedup ids, backoff and catch-up for the E9 verbs | 3 | 2 | 3 | 1 | 9 | already designed (F3.6, F3.7); no new item |

Why A1 scores low on fit and still wins on gain: a direct read of the board by a lane breaks I-5. The pipeline must own the store, check each entry against a schema, and copy entries into the index of a cell. The precedent is the L3 kind `recalled-lessons`, which already carries text from other cycles into a cell ([cell-context-index.md](../architecture/cell-context-index.md) §5). With that rule the fit is 2. The estimate is that the gain is the largest, but nobody counted it. Today a lane can retry a hypothesis that another lane falsified, and no path tells it (synthesis from F3.3 and F3.4).

Why A6 is deferred: at width 4 the integration is deterministic, and a width above 6 needs the group commit first (F3.9). An LLM integrator adds a seat and a review cost, with no measured conflict rate that asks for it. We open it when the condition of §7 holds.

Why A7 gets no item: the channel design gives the same guarantees as the Agensh router (F3.7), and the item `events-cli-verbs-e9` already covers the verbs. The replacement of the 5 s poll of `evolve wave watch` is in plan §9 (F3.6). The one gap that Agensh shows is A2.

## 6. Refinements to adopt

Each refinement is a proposal. Each one is a console-manual inbox item that links this file.

**R1 (proposed) A pipeline-carried knowledge board.** Item `agensh-knowledge-board`. From P2.6, F3.1, F3.3 and F3.4.

- An agent appends an entry through an `evolve` verb (the proposed name is `evolve board add`, agent class `A` of [cli-contract.md](../architecture/cli-contract.md) §4.1). The verb writes a declared artifact in the own workspace of the cell and is not a dispatch verb, so I-3 holds.
- The types are `FACT`, `FAIL`, `OBSERVED` and `PATCH_SUMMARY`. `CLAIM` is out (§4). An entry has a summary of 100 characters or fewer (300 for `PATCH_SUMMARY`), an optional detail, the item id, the cycle and the package cells.
- The pipeline validates each entry against a schema and appends it to a board store under `.evolve/`. Only the pipeline writes the store.
- The context index builder lists the recent entries for the cells of the item as L3 entries of kind `board`. On a retry of the same item, the `FAIL` entries of its lineage go into L2. The entries are untrusted data, never instructions.
- The pipeline copies the entries of the cells of the item into the inputs of the cell, as it does for `recalled-lessons`. Thus the sandbox needs no read grant on the board store. A read verb searches that copy.
- The proof: a test where lane A records `FAIL` for a hypothesis, and the index of lane B on the same cell lists that entry.
- The baseline (proposed): before the move to `enforce`, count the retries of a hypothesis that a `FAIL` of an earlier cycle recorded. When the count is 0 over one shadow wave, R1 stays at shadow.

**R2 (proposed) `ship.landed` at least once.** Item `agensh-ship-landed-outbox`. From P2.7 and F3.7.

- The `complete` intent records that the event is due. The emit marks it sent. A recovery emits each due event that has no sent mark, with the same event id, so a consumer drops the duplicate.
- The proof: a test stops the process between the intent write and the emit. After the recovery, it sees one `ship.landed` with the original id.

**R3 (proposed) A "no finding" reminder.** Item `agensh-no-finding-reminder`. From P2.8 and F3.5. It needs R1.

- When the phase has added no board entry, the idle nudge of the observer also asks for a `FACT` or a `FAIL` entry. The stall kill at `stall_s` does not change.
- The body is configuration, not code, in the observer policy.

**R4 (proposed) A staggered lane launch.** Item `agensh-staggered-lane-launch`. From P2.10 and F3.8.

- The wave orchestrator waits a configured gap between two lane starts. The default is a policy value, and 0 keeps the current behavior.
- R4 adds to the item `lane-test-floors-oversubscribe-the-host`, which addresses the recorded cause of F3.8. It does not replace that item.
- The measure: the boot time and the exit-80 count of each lane, for each gap, over one wave in shadow. The estimate is a small gain at width 4. We keep the gap only when the measure shows a lower exit-80 count.

**R5 (proposed) A differential certificate kind.** Item `agensh-differential-certificate`. From P2.11, P2.12 and F3.10.

- The new kind `differential` names a reference command, a candidate command and an input set. The audit runs both on each input and compares the outputs. A difference is a FAIL with the first input that differs.
- The reference is a fixed program at a pinned path or commit. The builder cannot change it (I-11 of ADR-0155).
- The first use is a port of a tool to a Go verb, with the old tool as the reference.

## 7. What changes our mind

| Evidence | What changes |
|---|---|
| A published ablation that credits the absence of an orchestrator, not the width or the board, with the gain | We reopen §4 and write an ADR that weighs I-3 and I-4 against the measured gain. |
| A repeat of the runs with a variance that puts the 1-agent and the 128-agent results inside one interval | We lower the evidence score of each option to 1 and hold R1 at shadow. |
| A cost for each agent that is more than the cost of our cycles for the same gain | We hold R1 and R4 at shadow and keep the width. |
| A width above 6, where the pairwise conflict rate of `evolve wave status` (ADR-0139 item 15) halves the window on most landings | We open A6, an integrator seat that the pipeline dispatches. |
| A shadow wave where lanes retry a `FAIL` entry that the index listed | R1 does not work as a read path. We move the entries into L1 for a retry, or we drop R1. |
