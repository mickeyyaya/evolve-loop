# ADR-0118 — An auto-response confirms a menu only on the choice it observes

- **Status:** Accepted (2026-10-05, console lane). Consumes inbox `trust-prompt-confirm-only-when-the-cursor-is-on-yes`. Extended the same day to codex's update menu ([addendum](#addendum-2026-10-05-codexs-update-menu)).
- **Supersedes nothing.** Refines how manifest `interactive_prompts` rules answer a menu, and what a boot wait does with the auto-responder's verdict.
- **Related:** the incident record [2026-09-01 claude 2.1.252 trust default flip](../../incidents/2026-09-01-claude-2252-trust-default-flip.md) (its 2026-10-05 section is this decision's evidence); [2026-08-27 plan-mode dialog blind spot](../../incidents/2026-08-27-plan-mode-dialog-blind-spot.md) (the bottom-anchor discipline both new rules keep); [ADR-0045 corrective interaction protocol](0045-corrective-interaction-protocol.md) (the send/outcome telemetry the rules feed); the bridge's [package notes](../packages/internal-bridge.md).

## Context

The bridge answers a CLI's interactive dialogs from data: each manifest rule pairs a regex over the pane with the keys to send, and the auto-responder ticks the rules against fresh captures. claude 2.1.252 and later show a folder-trust menu whose cursor starts on the destructive choice, "❯ No, exit". The rule for it, `trust_prompt_no_default`, sent `Down,Enter` as one burst and was fire-once.

A burst is open-loop: the Enter assumes the Down landed. On 2026-10-05 the Down reached claude before the dialog read input and was dropped; the Enter was not. It confirmed "No, exit", claude exited to the shell, and wave 59's readiness gate halted the loop (`bridge-boot` rc=80). A live probe on claude 2.1.285 adds a second fact: the menu's Down wraps (No → Yes → No), so even repeating the burst is unsafe.

The engine had three further gaps a repeatable rule exposes:

1. **Boot readiness was judged on a pane the tick had just changed.** claude's REPL marker is `❯`, the same glyph as the dialog's cursor. `bootTmuxREPL` re-polled only when a fire-once rule fired; a repeatable rule's send would let the boot wait see the dialog's `❯`, pass the dead-shell guard (claude still runs) and declare the REPL ready with the dialog up. The recipe adapter's `EnsureSession` never re-polled at all.
2. **The tick and the readiness check read different frames.** `bootTmuxREPL` captured a frame for the marker check and the tick captured its own; `EnsureSession` ticked first and then captured again for the marker check. In the recipe order, a dialog that mounts between the two captures is never answered: the boot returns on the earlier frame's marker, and the recipe's first command ends with an Enter that confirms "No, exit" (the architecture review's probe).
3. **Boot waits discarded the loop guard.** The engine already bounds every non-fire-once rule (`autoRespondLoopGuardLimit`, 5 matches per launch; the sixth returns rc 86). The artifact wait ends the run on it, but both boot waits ignored the tick's rc, so a stuck dialog ran out the 60 s boot deadline and reported a generic timeout.

## Decision

**1. One rule per observable menu state; the confirm key only on the wanted state.** A rule that answers a menu whose default (or any wrong selection) is destructive sends either navigation or confirmation, never both. Navigation rules match the menu with the cursor on a wrong choice and send one navigation key; they are not fire-once, so a lost or wrapped key is retried on the next tick that still shows the wrong choice. The confirm rule matches the menu with the cursor on the wanted choice and sends the confirm key. Each rule keeps the bottom anchor (footer, `\z`, `tail_lines`, distance bounds). The confirm rule is the strict one: it requires the wanted choice to be the only one the cursor marks. The navigation rule is the permissive one: any frame with a cursor on a wrong choice, including a torn redraw that shows a cursor on two lines, gets navigation. The rules are disjoint on every frame the menu renders, but text no build renders can still match two of them, so manifest order is the tiebreak: navigation rules come before the confirm rule, and an ambiguous frame gets navigation, never confirmation.

For claude's trust dialog this is `trust_prompt_cursor_on_no` (`Down`; any `❯ No, exit`) and `trust_prompt_cursor_on_yes` (`Enter`; an uncursored `No, exit` line directly above an unnumbered `❯ Yes, I trust this folder`), replacing `trust_prompt_no_default`. The first review found the confirm regex too loose: `No, exit.{0,80}❯ Yes, …` also matched a frame with a cursor on both lines, and only manifest order then kept it from sending Enter.

**2. The bound is the engine's existing loop guard.** No per-rule `max_fires` field: the loop guard already bounds every repeatable rule in every manifest with one number, and codex's plan picker relies on it the same way. A navigation rule that never moves the cursor trips it after five sends, without ever reaching the confirm rule.

**3. A boot wait shares one tick rule, `autoResponder.bootTick`, on one capture per pass.** Each pass of a boot wait captures the pane once and hands that frame to `bootTick`, which runs the tick on it (a failed capture is no observation: it is neither ticked nor judged, because tmux can return a frame alongside the error). A tick that sent keys returns "re-poll": the wait captures again on its next pass, whatever the rule's `once` setting. Only a pass that sent nothing judges readiness, on the same frame the rules saw. A tick that tripped the loop guard returns an error naming the rule and the guard's limit (the rule "matched more than 5 times": the guard counts matches, and an escalate rule sends nothing); `bootTmuxREPL` prints it as a FAIL line and exits `ExitREPLBootTimeout` (80), and `EnsureSession` returns it. The tick now returns the loop guard's action (`loop_guard:<name>`) with rc 86, so every caller can name the rule.

**4. A boot that ends on the loop guard is a boot timeout.** The REPL never reached its prompt, so the exit is the boot-timeout class the boot-failure bench counts (`clihealth.IsBootTimeoutExitCode`, exit 80): `recordBootStrike` records it and `clearBootStrike` does not clear the driver's strikes. A first draft exited `ExitRespondLoopGuard` (86); the engine reads every exit other than 80 as "the REPL booted", so a wall shown at boot, such as "Login expired", would never be benched and would wipe the driver's strikes each time. `IsBootTimeoutExitCode` keeps meaning 80 only: during a run, 86 means the REPL did boot.

## Alternatives considered

- **Keep the burst and add a pause between Down and Enter.** Still open-loop: a dropped Down is not fixed by waiting, and on a wrapping menu a delayed Down plus a retry lands back on No.
- **A per-rule `max_fires` field.** It would duplicate the loop guard with a second knob that every manifest author must remember to set; nothing needs a different budget today.
- **A hotkey that selects Yes directly.** The 2.1.252+ options are unnumbered, and no hotkey was verified live; an unverified keystroke is the class of error this rule exists to prevent (the plan_approval note's reasoning).
- **Pre-trust the folder in `~/.claude.json` before launch.** It would skip the dialog the way `pretrustCodexProjects` does for codex, but it writes a host-global file the CLI owns and whose schema is undocumented, and the dialog still needs a correct answer whenever pre-trust misses. Worth its own item if the dialog keeps costing boots.
- **Make the confirm rule fire-once.** A lost Enter would then leave the dialog up with its `❯`, and the boot wait would treat it as the REPL marker. Because Enter only ever goes to a pane that shows the cursor on Yes, repeating it is safe.

## Consequences

- An Enter can reach claude's trust dialog only on a capture that shows the cursor on Yes. A dropped Down costs one boot tick (1 s).
- Any boot-time rule that sends keys now costs one extra boot poll before readiness is judged; a fire-once rule already did. Each boot pass captures the pane once instead of twice. A non-fire-once rule that keeps matching a healthy boot screen now ends the boot on the loop guard; before, the boot passed on the marker and the wait loop's guard abandoned the run a few ticks later, unless the prompt paste scrolled the match away. The 67 loop logs on the runtime plane (2026-09-02 to 2026-10-05) record no boot-time send other than the trust rules (the two `per_edit_approval` sends were mid-run).
- A dialog the auto-responder cannot move, or an escalate prompt that never clears at boot, ends the boot in about six seconds with `ExitREPLBootTimeout` and a FAIL line naming the rule, instead of the same exit after 60 s with no cause. The exit stays a boot-timeout strike, so the boot-failure bench (`DefaultBootBenchThreshold`, two consecutive strikes) benches a driver whose boot keeps hitting the same wall, as it did before, only sooner.
- Residual: a Down still unrendered a full boot interval after it was sent could wrap the cursor back between the capture that showed Yes and the Enter. That needs render latency above 1 s twice in a row; the live dialog moved in well under 0.5 s.
- The codex and agy manifests have no navigate-then-confirm burst on a destructive-default menu (their trust rules answer Yes-default menus with an absolute hotkey or a bare Enter), so they keep their rules.

## Addendum (2026-10-05): codex's update menu

- **Status:** Accepted (2026-10-05, console lane), revised the same day after the architecture review (Decisions 4 to 6) and its re-review (Decision 5: the hold is boot-only and last). Consumes inbox `codex-update-menu-never-confirms-update` and `boot-smoke-launches-without-the-manifest-realization`. Evidence: [incident 2026-10-05 codex update menu](../../incidents/2026-10-05-codex-update-menu.md).

### Context

The same day, every codex launch of wave 59b failed on codex 0.153.4's startup update menu, a numbered menu whose cursor starts on the destructive choice, `1. Update now`, which runs `brew upgrade --cask codex`; inside the sandbox the upgrade fails and codex exits to the shell. The Consequences above said codex had no navigate-then-confirm burst; it had something worse, outside the manifest altogether: `bootTmuxREPL` sent the codex driver's `bootMenuSkip` key, `2`, with Enter, whenever a boot pass's 200-line capture contained the menu's words anywhere. That check had no bottom anchor, so it kept firing on the answered menu in the scrollback above the composer, and a `2` dropped before the menu read input would have let its Enter confirm `Update now`. Most launches never reached it: codex draws its composer, `›` marker and all, before the menu mounts, so the boot declared readiness on the composer and the prompt's submit Enter confirmed `Update now`.

### Decision

1. **Prevent the menu per launch.** The codex-tmux manifest's `default_args` carry `-c check_for_update_on_startup=false`, a top-level codex config key, so every realized codex launch starts with codex's update check off. Verified live on 0.153.4: with the same `~/.codex/version.json`, the menu shows without the override and never with it. The override is launch data, not a Go literal, and writes no host-global file.
2. **Answer the menu, when it shows anyway, by this ADR's rule.** `update_menu_cursor_off_skip` sends `Down` on a cursor on `1. Update now` or `3. Skip until next version` (the live menu wraps 1 → 2 → 3 → 1, so option 3 reaches Skip in two Downs) and is permissive: a torn redraw with two cursors gets Down. `update_menu_cursor_on_skip` sends `Enter` only on `› 2. Skip` with uncursored options 1 and 3 around it and is strict. Both are bottom-anchored on the `Press enter to continue` footer (`\z`, `tail_lines` 8), so the answered menu above the composer matches neither, and navigation precedes confirmation in the manifest. The loop guard bounds both, and a cursor that never moves ends the boot as a boot timeout (Decision 4 of the original decision above).
3. **No boot path answers a dialog outside the manifest rules.** `tmuxLaunch.bootMenuSkip`, its send in `bootTmuxREPL` and `tmuxPaneLooksLikeUpdateMenu` are deleted. The claude and agy drivers and the recipe boot have no bespoke boot-menu path; their boot dialogs are manifest rules ticked through `bootTick`.
4. **The smokes launch what a phase launches.** The prevention in Decision 1 reached only realized launches, and the boot smoke (the readiness gate, `evolve doctor boot`) and the live smoke (the CLI-health canary, `evolve doctor live`) were launched with no realization, so the canary still met the menu and misread codex. `BootSmokeTest` and `LiveSmokeTest` now share `smokeLaunchConfig`: when the caller supplies no realization, it realizes the driver's manifest with the bypass intent the smokes already assume, so codex carries `--yolo` and the override, claude and agy `--dangerously-skip-permissions`, and claude's `default_env` is exported. A caller's own realization is launched unchanged.
5. **A menu no rule can parse fails closed.** Readiness is the prompt marker, and codex's marker `›` is also the menu's cursor, so a menu the shaped rules miss (a reworded footer, an extra line) was declared ready on its own cursor and the prompt's Enter confirmed `Update now`. A new policy, `hold`, sends nothing and makes a boot wait re-poll instead of judging readiness on the frame (`bootTick` treats it as a send; the artifact wait keeps waiting); the loop guard then ends the boot as a boot timeout naming the rule, the shape of an escalate prompt that never clears. An `escalate` rule would not do: a boot judges the marker on an escalate frame (claude's "Login expired" notice on a live REPL must not block readiness), and on this menu the marker is present. codex's `update_menu_unparsed` holds any frame whose last 24 lines start a line with the `Update available!` header with at most one `›` after it, so it lets go once the composer, with its own `›`, is drawn below the answered menu. A busy pane is never held. **The hold is boot-only:** once boot readiness is declared, `autoResponder.endBoot` drops every hold rule from the responder, at the tmux boot (`bootTmuxREPL`, including a resumed named session) and at the recipe boot (`EnsureSession`, including an attach). The rule has no footer anchor, so in a run phase an idle pane whose agent quotes the header, with the composer's `›` below it, matched on every tick (the re-review's probe: rc 4 five times, then 86) and the artifact wait abandoned the run on the loop guard ahead of the idle-artifact nudge that would have recovered it; the follow-up items send codex agents to exactly this text. **The hold is the manifest's last rule:** first-match order would otherwise let it take a frame that keeps the header without its cursor from `trust_prompt`, `per_edit_approval`, `auth_recheck`, `rate_limit`, `model_unsupported` or `plan_question`.
6. **A self-match guard slides the pane bottom over every line.** The rules are bottom-anchored, so a guard that runs them on a whole tracked file only tests that file's last lines; a pane can stop anywhere inside a printed file. `requireNoRuleFiresAtAnyPaneBottom` runs the rules through `decideAutoRespond` on the 64 lines ending at every line of each file (it requires every rule's `tail_lines` to fit in 64). The update-menu and claude trust guards use it. On its first run it found two claude test fixtures that quote the numbered trust dialog flattened with `\n` escapes, which `trust_prompt` matched; that rule now needs its cursor line and its footer to begin a line. The incident record's capture of the menu carries a `│` gutter for the same reason.

### Alternatives considered

- **Keep the hotkey, alone.** The digit `2` selects Skip on the live menu without an Enter, and a lost `2` is retried on the next tick. Rejected: a `2` sent from a frame captured just before the menu closed types into the composer and prefixes the prompt, and the old path that used the hotkey is the one that matched stale scrollback. A Down or an Enter that reaches an empty composer does nothing.
- **Write `dismissed_version` as the latest version into `~/.codex/version.json`.** It is a host-global file that codex itself rewrites, and the `999.999.999` sentinel the preflight already writes stopped working without an error. The per-launch override needs no shared state.
- **Set `check_for_update_on_startup = false` in `~/.codex/config.toml`.** It would cover launches the manifest does not realize, but it is a host-global write to a file the CLI owns, the trade-off this ADR declined for claude's `~/.claude.json`. Decision 4 closed that gap instead: every smoke now realizes the manifest.
- **Answer an unparsed menu with an `escalate` rule.** It ends a live run at once (exit 85), but at boot an escalate verdict leaves readiness to the marker, and this menu shows the marker. Changing that would block readiness on every escalate notice a booted REPL shows.
- **Pin `tail_lines` by dropping it.** `\z` and the distance bounds already confine both shaped rules to the bottom of a frame codex renders; `tail_lines` additionally bounds how far above the footer the options may sit, and a frame that only it rejects is held rather than answered. It is kept, consistent with the claude rules, and pinned by its own test.
- **Rely on the Homebrew pin.** The cask is pinned and the upgrade fails, but the menu still shows and its default still exits codex.

### Consequences

- A codex phase launch no longer shows the update menu; if a build ignores the key, the menu costs a Down and an Enter instead of the session.
- `dismissCodexUpdateNag` no longer keeps the menu away. It stays: the readiness gate's freeze check reads the presence of `~/.codex/version.json`, and codex, with its update check off, no longer writes that file itself (the live probe left it unchanged).
- The readiness gate, `evolve doctor boot`, the CLI-health canary and `evolve doctor live` now launch claude and agy with `--dangerously-skip-permissions` and export claude's `default_env`, as their phase launches do; before, they booted the bare binaries.
- A codex boot that meets an update menu no rule parses now ends in about 12 s (six holds at the 2 s boot interval) as a boot-timeout strike naming `update_menu_unparsed`, instead of booting onto the menu. After readiness the hold is gone, so a run phase never ends on it.
- Residual: codex draws its composer before any startup dialog, so readiness can still be judged before a dialog mounts and the prompt's Enter can reach it; the hold only sees a menu a boot pass captures. The update menu no longer shows and the bridge pre-trusts each worktree, so no known dialog takes that path today (inbox `codex-readiness-judged-on-the-composer-drawn-before-a-startup-dialog`, whose acceptance now includes an unparsed dialog at the pre-submit capture). `dismissCodexUpdateNag` keeps a name and a sentinel write that are both false now (inbox `codex-version-state-file-without-the-dead-dismissal-sentinel`). The plan-mode self-match guard still reads whole files (inbox `plan-mode-self-match-guard-checks-only-the-end-of-each-file`).
