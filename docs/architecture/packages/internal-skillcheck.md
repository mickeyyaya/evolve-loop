# internal/skillcheck

## Purpose

`internal/skillcheck` is the projection half of [ADR-0040](../adr/0040-skill-naming-and-single-source-projection.md): it renders every generated plugin surface from its single source and either writes it (`evolve skills generate`) or reports drift (`evolve skills check`). It lives outside `cmd/evolve` so the CLI and the cycle's audit phase run the same drift check in-process; the audit, an internal package, cannot import package main. `Run` is the CLI path and `Check` is the print-free gate the audit calls.

## Design

- **Four surfaces, one check.** `Run` and `Check` both cover: the `GENERATED:phase-facts` region of each phase `SKILL.md`; a `commands/<name>.md` stub per skill; the two Codex manifests; and the membership of `.claude-plugin/plugin.json` (`ManifestProblems`). `inspect` is the pure seam both build on: it renders and compares, and never writes or prints.
- **Run's exit codes.** 0 when in sync (check mode prints the `check OK` line) or after a write; 2 in check mode for any drift, frontmatter-name mismatch or manifest problem; 1 on an infrastructure error. `DRIFT:` lines go to stderr only (`TestRun_CheckMode_Drift_OutputIsolation`); `characterization_test.go` pins the exact output lines. Manifest problems are not auto-fixable, so they fail check mode and never the write path.
- **Check's error contract.** `Check` returns the drifted rel-paths plus name and manifest messages; its error is non-nil only on an infrastructure fault (catalog, template or read failure), so the audit fails open on infrastructure and fails on real drift.
- **Phase-facts regions.** Only the built-in phase skills in `phaseSkillDirs` carry a generated region (`retrospective` maps to `skills/retro`); the macro `skills/loop` and the utility skills are pipeline-wide or phase-agnostic. Each `skillFacts` field traces to one source (ADR-0040 §2): the merged phase catalog and the registry's raw `role` key (`registryRoles` — `PhaseSpec` maps JSON `archetype` onto its `Role` field and does not carry the registry's profile name), the dispatch profile `.evolve/profiles/<role>.json` (CLI, tier, and the un-modeled `parallel_subtasks` array read from `profiles.Profile.Raw`), and `phasecontract` (artifact, sections with their tolerated legacy headings, verdicts; `FromSpec` derives a user phase's contract). Phases render in sorted order so output is deterministic.
- **Fact collection is fail-soft.** A missing profile, persona or registry renders as a gap, never an error; drift detection decides what is fatal. An unknown role falls back to the phase name. `personaPath` tries `spec.Agent`, then `agents/evolve-<role>.md`, then `agents/<role>.md`, and is empty for native phases such as ship. A phase with no declared output files gets no artifact name, because `FromSpec`'s `<phase>-report.md` default would be fiction (ship's deliverable is the commit) (`TestCollectSkillFacts_UserPhaseArtifactName`).
- **Frontmatter name rule.** `nameMismatches` enforces ADR-0040 rule 3: every skill dir's `SKILL.md` frontmatter `name` equals the directory name. A dir without `SKILL.md` is not a skill.
- **Marked-region splice.** `SpliceMarkedRegion` is shared by `evolve skills`, `evolve flags` and `evolve signals` (the last two pass no anchor). It replaces exactly one BEGIN/END pair; a BEGIN without END and a second BEGIN (a botched manual merge) are errors rather than an orphaned stale region. It swallows one trailing newline after END so regeneration is idempotent, which requires the block to carry its own markers (`TestSpliceMarkedRegion_IdempotentWithMarkers`, `TestSpliceGeneratedRegion_Idempotent`). Without markers the block goes before the fallback anchor (`\n## Composition` for skills), or is appended. The insert point is one byte into the anchor, so a non-empty anchor must begin with `\n`.
- **Command stubs.** Every skill projects to a bare `commands/<name>.md`: Claude Code namespaces a plugin command as `/<plugin>:<basename>`, so `loop.md` in the `evo` plugin surfaces as `/evo:loop`, matching `.evolve/naming.json` `canonical.commandPrefix` and the Skill tool id `evo:loop`; an `evo-` prefix would double to `/evo:evo-loop`. `CommandFileName` and `RenderCommandStub` are the single source for the filename and the stub, shared with the agy cross-CLI publisher (`cmd/evolve/cmd_skills_publish.go`). The stub carries only the skill's `description` and `argument-hint` for the `/` menu and a body that delegates to the skill; `SKILL.md` stays the single source. A skill with unparseable frontmatter gets no stub (`nameMismatches` reports it); a nameless one stubs to its dir name.
- **The generated marker is the reap guard.** An orphan `commands/*.md` (no backing skill) is removed only when it carries `commandGenMarker`, so a hand-authored command is never reaped (`TestRun_OrphanCommand`). A skill-backed `<skill>.md` is reserved and always overwritten to track its skill. Marker-bearing legacy `evo-<skill>.md` stubs are orphans and get reaped (`TestRun_LegacyPrefixedStubReaped`).
- **Stub frontmatter quoting.** `yamlQuote` emits a YAML double-quoted scalar, escaping backslash, the quote, and newline, CR and tab. YAML folds a raw newline to a space, so an unescaped multi-line description would never re-match its source and would drift forever. Colons, slashes and backticks are already safe inside double quotes.
- **Codex manifests.** `.codex-plugin/plugin.json` and `.agents/plugins/marketplace.json` are generated from `.claude-plugin/plugin.json`, never hand-edited, so a Codex install gets the same skill set from the same source. Codex's native plugin system mirrors Claude Code's: `codex plugin marketplace add mickeyyaya/evolve-loop` reads the repo-root marketplace, and `codex plugin add evo@evo` reads the plugin manifest (`"skills": "./skills/"`). `source.path` is `.` (the repo root is the plugin) rather than a vendored copy, which keeps the skills single-sourced under `skills/` at the cost of `marketplace add` fetching the whole repo. Output is deterministic: struct field order, two-space indent and a trailing newline. A checkout without the Claude manifest is not a plugin repo, and the projection is a no-op (`TestCodexManifestDiffs_ToleratedAbsentSource`).
- **Codex schema constraint.** Codex's strict marketplace schema accepts only `ON_INSTALL` or `ON_USE` for `authentication` (not `NONE`); evo needs no auth, so it emits `ON_USE` (`TestRenderCodexMarketplace_StrictSchemaConformance`).
- **Release lockstep.** `internal/versionbump` bumps the Codex manifest's version at release with a surgical replace that preserves this package's formatting, so `generate` and the release bump stay byte-identical (`TestRun_BumpsCodexPluginJSON`); a stale Codex version is drift (`TestCodexManifestDiffs_DetectsVersionDrift`).
- **Manifest membership.** `ManifestProblems` requires `.claude-plugin/plugin.json`, the list Claude Code's loader reads, to be a bijection with the skill dirs on disk: every `skills[]` entry is a well-formed `./skills/<name>/` with a backing `SKILL.md` and appears once, every dir holding a `SKILL.md` is listed, and every `agents[]` path resolves. The other surfaces all source from disk, so a dir the manifest omits passes them and is invisible to the loader ("Unknown skill"). Frontmatter validity is left to `nameMismatches` so one defect is not reported twice. An absent manifest is a skip (not a plugin tree); an unreadable or corrupt one is a problem string (fail-closed); only an unreadable `skills/` dir is an error. Problems are sorted.

## Invariants

- **`skillEntryName` rejects `.`, `..` and embedded separators,** so `./skills/..` cannot resolve to `<root>/SKILL.md` and pass falsely (`TestManifestProblems_DotDotSkillEntryRejected`, `TestSkillEntryName`).
- **The live tree is in sync.** `TestCheck_CleanRepoNoDrift` and `TestManifestProblems_CleanRepoNoProblems` are the in-process equivalents of CI's `evolve skills check`; a skill added to disk but not registered, or a hand edit inside a generated region (`TestCheck_DetectsMutatedRegion`), turns them red.
- **Multi-line descriptions round-trip through `yamlQuote`.** No test pins this yet (a one-line why stays on `yamlQuote`).

## Findings

- **Manifest tests inject one defect each.** Every `TestManifestProblems_*` mutation case builds a minimal synthetic tree with exactly one defect and asserts a defect-specific message, not just the skill name, so each test fails only on the path it names. `manifestDefectTree` registers a skill the tree does not provide (`ghostskill`), which only the membership surface can see, to prove the `Run` and `Check` wiring.
