## Purpose

`internal/bridge` launches and drives the LLM CLIs a phase runs on (claude, codex, agy, ollama), headless or inside a tmux REPL. It realizes a phase's launch intent into per-CLI flags from embedded manifests, answers or escalates the interactive prompts a REPL raises, detects walls and wedges, and records each launch attempt's telemetry.

*File group 1: `attempt_telemetry.go`, `autorespond.go`, `billing.go`, `bootsmoke.go`, `budget_scale.go`, `capture_models.go`, `catalog_overlay.go`, `clicontrol_adapter.go`, `codex_model_clamp.go`, `codex_pretrust.go` and their tests.*

### Auto-responder (`autorespond.go`)

The auto-responder is the fallback prompt engine for interactive REPLs, a port of `lib/auto-respond.sh`. `--dangerously-skip-permissions` is the default permission strategy; the responder is the safety net for the prompts that escape it: auth rechecks, rate limits, model deprecation, trust dialogs, plan mode and the like. It has two layers:

- `decideAutoRespond` is pure: pane, manifest `interactive_prompts`, and per-rule match counts in; an action and an rc out.
- `autoResponder.tick` / `tickPane` is effectful: capture the pane (or take the wait loop's capture), decide, then send keys or write `escalation-report.json`.

The action and rc contract `runTmuxREPL` consumes:

| Action | rc | Meaning |
|---|---|---|
| `noop` | 0 | nothing matched |
| `suppress_once:<name>` | 0 | only a handled fire-once prompt still matches; the caller warns once |
| `send:<csv>` | 1 | keys were sent (the caller sees `""`, 1) |
| `extend:<secs>` | 2 | push the artifact-wait deadline |
| `hold:<name>` | 4 | a `hold` rule matched a dialog no rule can answer: nothing is sent (the caller sees `""`, 4), and a boot wait re-polls instead of judging readiness on the frame until the loop guard ends the boot. Hold rules exist only during a boot: `autoResponder.endBoot` drops them once readiness is declared |
| `transient_dwell` | 3 | a transient upstream error held for the dwell (enforce stage only) |
| `escalate:<name>` / `escalate:exhausted` | 85 | escalate policy, missing or invalid keys, or a confirmed quota wall |
| `loop_guard:<name>` | 86 | one rule matched more than 5 times in the launch (the caller sees the action, so it can name the rule) |

The loop guard counts every match of the same rule across the launch, not consecutive sends; [full-tmux-control.md §2a](../full-tmux-control.md) describes it as "5 consecutive sends without pane progression", which is looser than the code. It is the one bound on every repeatable rule in every manifest; there is no per-rule budget.

The boot waits (`bootTmuxREPL` for a phase launch or boot smoke, and the recipe adapter's `EnsureSession`) capture the pane once per pass and read the tick through one method, `autoResponder.bootTick`, which runs the tick on that frame; a failed capture is no observation, neither ticked nor judged (`execTmux` can return a frame alongside the error). A tick that sent keys (rc 1), or that a `hold` rule matched (rc 4), makes the wait capture again on its next pass, because a dialog's selection cursor can be the marker itself (claude's `❯`) and a repeatable rule leaves the dialog up between ticks; only a pass that sent nothing judges the prompt marker, on the frame the rules saw. A tick that tripped the loop guard (rc 86) returns an error naming the rule and the guard's limit ("matched more than 5 times": the guard counts matches of any rule, escalate rules included, which send nothing): `bootTmuxREPL` prints it as a `FAIL` line and exits `ExitREPLBootTimeout`, the boot-timeout class the boot-failure bench counts (an exit 86 would read as "booted" to `clearBootStrike` and `recordBootStrike`), and `EnsureSession` returns it. Any other verdict, rc 85 included, leaves the wait to judge the marker as before ([ADR-0118](../adr/0118-confirm-a-menu-only-on-the-observed-choice.md)).

Rule selection:

- **A manifest declares what its driver cannot do.** `toolless: true` (ollama-tmux) means the CLI has no tool use and cannot write a worktree artifact; `HasToolUse` is the one predicate over it, failing closed (a CLI whose manifest does not load has no proven tool use), used by the ollama launch guard and by the universal-fallback tail. Every lane phase runs in its worktree (CB.1), so the guard refuses a lane phase for want of tool use, not because the phase writes source. Pinned by `TestHasToolUse_FollowsTheDriverManifest`.
- The first manifest rule whose regex matches wins, so manifest order is part of the contract. A rule with `tail_lines` matches only the tail of the capture, where a live modal sits.
- An `escalate` or `hold` match on a busy pane is skipped: a CLI cannot be blocked on a prompt while it is generating, so the match is the agent quoting a banner or a dialog ([ADR-0047](../adr/0047-surface-classification-and-channel-separation.md)). Only those two are gated; approvals and menus render beside their own "esc to cancel".
- **A dialog no rule can parse fails closed** (`hold`, [ADR-0118 addendum](../adr/0118-confirm-a-menu-only-on-the-observed-choice.md#addendum-2026-10-05-codexs-update-menu)). A `hold` rule sends nothing; `bootTick` treats it as it treats a send (re-poll, never judge readiness on that frame), so a dialog whose own cursor is the prompt marker cannot be declared the REPL, and the loop guard ends the boot as a boot timeout naming the rule. **A hold is boot-only:** `autoResponder.endBoot` drops every hold rule from the responder once boot readiness is declared, at both readiness points (`bootTmuxREPL`, including a resumed named session, and the recipe's `EnsureSession`, including an attach), because in a run phase an idle pane whose agent quotes the dialog's header would otherwise be held on every tick and the loop guard would abandon a run the idle-artifact nudge could recover. codex's `update_menu_unparsed` is the manifest's last rule, so it shadows no rule that can answer a frame it also matches (a cursorless menu above the trust dialog gets `trust_prompt`), and holds any frame whose last 24 lines start a line with the menu's `Update available!` header and carry at most one `›` after it: the shaped rules answer every menu they parse, the hold takes the rest (a reworded footer, an extra line), and it lets go once codex draws its composer, with a second `›`, below the answered menu.
- A `once: true` rule fires one time. Its dismissed text lingers in the re-captured scrollback, so later matches are skipped without counting toward the loop guard, and the scan continues so a new prompt still fires.
- **A menu is confirmed only on the choice the pane shows** ([ADR-0118](../adr/0118-confirm-a-menu-only-on-the-observed-choice.md)). A rule for a menu whose default or a wrong selection is destructive sends navigation or confirmation, never a burst of both: navigation rules match the cursor on a wrong choice and send one key, repeatable and bounded by the loop guard; the confirm rule matches the wanted choice only when it is the one the cursor marks. The navigation rule is permissive (a torn redraw with two cursors gets navigation), the confirm rule strict, and navigation precedes confirmation in the manifest: the rules are disjoint on every frame the menu renders, and order is the tiebreak for text it never renders. claude's unnumbered trust dialog is `trust_prompt_cursor_on_no` (`Down`; any `❯ No, exit`) and `trust_prompt_cursor_on_yes` (`Enter`; an uncursored `No, exit` line directly above `❯ Yes, I trust this folder`); the live 2.1.285 dialog wraps its Down (Yes → No), so a blind repeat could land on No, and a lost Down now costs one boot tick instead of the REPL. codex's startup update menu is `update_menu_cursor_off_skip` (`Down`; a cursor on `1. Update now` or `3. Skip until next version`) and `update_menu_cursor_on_skip` (`Enter`; an uncursored `1. Update now` line directly above `› 2. Skip` and an uncursored option 3 below it), both bottom-anchored on the `Press enter to continue` footer (`\z`, `tail_lines` 8); the live 0.153.4 menu wraps its Down (1 → 2 → 3 → 1), so a cursor on option 3 reaches Skip in two Downs, and an Enter can never confirm `Update now`, whose `brew upgrade` fails in the sandbox and exits codex to the shell. **No boot path sends keys outside the manifest rules:** the codex boot used to send the hotkey `2` with Enter on any pane that contained `Update available!`, `Update now` and `Skip` anywhere (`bootMenuSkip`, `tmuxPaneLooksLikeUpdateMenu`); the answered menu stays in the scrollback above the composer, so that check typed `2` and Enter into the composer on every boot pass until the boot timed out. Both are deleted ([ADR-0118 addendum](../adr/0118-confirm-a-menu-only-on-the-observed-choice.md#addendum-2026-10-05-codexs-update-menu)).

Pane treatments, applied before matching:

- `decideAutoRespond` strips agent diff lines: a numbered editor diff line or a bare `+`/`-` line. `+++`/`---` headers pass. CLI chrome is never diff-prefixed.
- `tickPane` strips prompt-echo lines, a line whose trimmed text is a substring of the injected prompt, before both the prompt match and the exhaustion scan. An empty prompt strips nothing.
- `strippedForExhaustionScan` (echo strip, then diff strip) is the one treatment both exhaustion scans use: the tick fast path and the stop-review checkpoint in `driver_tmux_repl.go`.
- `strippedForFatalPaneScan` delegates to `recovery.StripAgentContent`; see [internal-recovery.md](internal-recovery.md) for why it differs.
- The raw pane is kept for pending-send resolution, shadow rules, the busy probe and the escalation report.

The busy read goes through `LivenessCenter.BusyOf`, which is nil-safe and stateless, so the tick never disturbs the stop-review checkpoint's `Observe` baseline and the Center stays the only liveness facade ([ADR-0068](../adr/0068-bridge-signal-center-concurrency.md)).

Each tick also runs three detectors on the stripped pane:

- **Quota wall.** The manifest's `exhausted_regex` is checked through `LivenessCenter.ExhaustedOf`, ungated by busy, and overrides a lesser verdict because the artifact will never come. A wall must persist for consecutive observations (`exhaustion_persistence.go`), then one live probe corroborates it (`wallcorroborate.go`; the production corroborator is wired in [internal-adapters-bridge.md](internal-adapters-bridge.md)). A healthy answer disables the scan for the phase; a confirmed wall escalates `escalate:exhausted`.
- **Transient upstream dwell.** The manifest's `transient_regex` on a non-busy frame for 30 consecutive wait-loop observations (60s at the 2s cadence) records `would_fast_fail` in shadow and returns rc 3 in enforce (the recovery stage, `Deps.RecoveryStage`). Only the artifact wait loop enables it.
- **Shadow rules.** Promoted rules at shadow stage match observe-only and record `rule_shadow_fire` / `would_fire` once per rule per launch, the evidence the batch-end auto-enforce sweep reads.

Interaction telemetry ([ADR-0045](../adr/0045-corrective-interaction-protocol.md) I1): every send opens a pending outcome that the next capture resolves. The pattern clearing records `prompt_cleared`; the loop guard tripping on the same rule, or a new send while one is pending, records `no_effect`; a lingering fire-once prompt records `suppressed_lingering`; the run ending records `run_ended`. The recipe adapter's capability runs carry no recorder.

The AskBroker rung ([ADR-0045](../adr/0045-corrective-interaction-protocol.md) I3) runs before any rc 85: it extracts the blocking question through `panetrust` (typed extraction; the privileged path never branches on raw pane text) and asks the `KernelAnswerer`. In enforce it injects the answer once per launch and returns rc 1; in shadow it records `would_act` on every tick that reaches it; off, a nil broker, no typed question or a miss escalate as before.

Keys: `sendKeySequence` sends each comma-separated token as its own keystroke with a 500 ms pause through `Deps.Sleep`; an `Enter` token is a bare Enter. Human mode adds a reading pause and human-cadence typing.

The decision-matrix fixtures in `autorespond_decision_test.go` are verbatim panes from claude v2.1.150, codex v0.133.0 and agy 1.0.2, recorded in [tmux-repl-cli-behavior-2026-05-26.md](../../research/tmux-repl-cli-behavior-2026-05-26.md).

### Attempt telemetry (`attempt_telemetry.go`)

`recordModelAttempt` writes the one `llm-calls` ledger row per launch attempt (`llmcalls` owns the filename and I/O). It derives the attempt number (at least 1) and the call id once and returns the `attemptLogContext`, so every later signal of the same launch carries the row's identity. Usage status follows the resolver's source: transcript or events result is `measured`, scrollback peak is `partial`, anything else is `unavailable`, and a resolver error is `resolver_error`. Negative counters and a NaN or infinite fill are discarded with a warning. `launchWarn` is the only `bridge.warning` producer; `tripwire` emits `bridge.tripwire` when a successful non-claude launch runs past `tripwireSuccessThreshold` with no usage source. The ledger's cause code comes from `launchoutcome.CauseCode` ([decomposition unit 10](../decomposition/10-bridgeengine.md), [ADR-0101](../adr/0101-signal-center.md)).

### Codex launch preparation (`codex_pretrust.go`, `codex_model_clamp.go`)

- **Pretrust.** codex-tmux's `Preflight` runs `pretrustCodexProjects` and `dismissCodexUpdateNag` at the engine's `CLIPreflight` chokepoint, strictly before the driver's `Launch`, for the exact worktree of every launch: fresh, reused or resumed. A provisioning-time hook was rejected: it would duplicate the same write through a new core→bridge seam (core cannot import bridge) for no behavioural gain. The recipe path (`newRecipeDriver`) bypasses `CLIPreflight`, so it pretrusts codex-family CLIs itself.
- The pretrust appends `[projects."<path>"] trust_level = "trusted"` for the worktree and workspace, plus `[notice] hide_rate_limit_model_nudge = true`, to `~/.codex/config.toml`. The merge is append-only and idempotent. The directory is created 0700 and the file written 0600 through a unique temp file and rename. `dismissCodexUpdateNag` sets `dismissed_version` in `~/.codex/version.json` to the sentinel `999.999.999`; on codex 0.153.4 that no longer hides the update menu (the menu showed with that sentinel and `latest_version` 0.160.0 on file, 2026-10-05). What keeps the menu away is the launch itself: codex-tmux's manifest `default_args` carry `-c check_for_update_on_startup=false`, a top-level codex config key, so every realized codex launch (a phase launch, the clicontrol recipe, and every boot or live smoke, which realize the manifest when their caller supplies nothing) starts with codex's startup update check off, and no host-global file is written for it. The update menu rules above are the defence when the menu shows anyway. Pinned by `TestCodexLaunch_ArgvCarriesTheUpdateCheckOffOverride` and `TestRealizeFor_RealManifests_NoCrossCLILeak`.
- **Model clamp.** A ChatGPT-subscription codex account rejects models outside its plan. `clampCodexModelForAuth` rewrites the effective model selector (split or inline `-m`/`--model`, or a `-c model=` override; a dedicated flag beats an override) to the manifest's `chatgpt_default_model` when the model is not in `chatgpt_safe_models`. Auth is `api-key` only when `OPENAI_API_KEY` is set and `BRIDGE_ALLOW_OPENAI_API_KEY=1`; the credential-isolation guard already demands that opt-in, so the env alone decides.

### Other surfaces

- **Boot smoke** (`bootsmoke.go`). `BootSmokeTest` runs a `*-tmux` driver's real `Launch` with `BootOnly` and bypass-equivalent posture, and exits without a prompt, so the boot is the one a phase launch performs. It returns `ExitOK`, `ExitREPLBootTimeout` (the deadline passed, or a boot-time rule tripped the loop guard), `ExitMissingBinary`, or `ExitBadFlags` for an unknown or non-tmux driver, plus the final scrollback. It self-provisions and removes a scratch workspace and boots in a scratch cwd. `evolve doctor boot` and the loop readiness gate both show its `ScrollbackTail`. `BootSmokeTest` and `LiveSmokeTest` (the CLI-health canary and `evolve doctor live`) share `smokeLaunchConfig`: both run bypass-equivalent, because their task is inert and the safety gate requires it, and a caller that supplies no `Realization` (the readiness gate, `evolve doctor boot`, the canary and `evolve doctor live` supply none) gets the driver's manifest realized with the bypass intent, so the smoke launches what a phase launches: codex with `--yolo` and `-c check_for_update_on_startup=false`, claude and agy with `--dangerously-skip-permissions`, claude's `default_env` exported, ollama with `--experimental-yolo` (whose launch guard then refuses the scratch worktree, as it refuses every lane phase). A caller's own realization is launched unchanged. Pinned by `TestBootSmokeTest_ACallerWithNoRealizationLaunchesCodexWithTheManifestsArgs`, `TestLiveSmokeTest_ACallerWithNoRealizationLaunchesCodexWithTheManifestsArgs`, `TestBootSmokeTest_ACallerWithNoRealizationBootsClaudeAndAgyAsAPhaseLaunchDoes`, `TestBootSmokeTest_ACallerWithNoRealizationGetsOllamasDefaultArgs`, `TestBootSmokeTest_ACallerRealizationIsLaunchedUnchanged`, and at the callers `TestCLIHealthCanaryProbe_LaunchesCodexWithItsStartupUpdateCheckOff` (cmd/evolve) and `TestDoctorLive_LaunchesCodexWithItsStartupUpdateCheckOff` (internal/cli/opscmd).
- **Boot handshake** (pinned in `boot_handshake_test.go`). Boot is ready only when the prompt marker is visible and the pane's foreground process is not a shell. The shell set is closed while CLI binary names vary (claude runs under node), so the check rejects a known shell rather than requiring a known binary, and a controller without `PaneCommander` degrades safely. After the paste, the first wait-loop pane showing shell-spill signatures with a shell process fails fast with `ExitREPLBootTimeout`; spill-lookalike text under the CLI process is ignored. The real driver constructors arm `guardDeadShell`; the RealTmux integration fixtures, whose REPL is a shell script, run with it unset. Mid-run process death is the observer's job.
- **Idle-artifact nudge** (pinned in `bridge_dialog_autorespond_test.go`). When a review checkpoint finds the agent idle with the artifact missing, the driver sends exactly one in-pane nudge naming the artifact path before the timeout path proceeds: the agent has often finished and not written the file.
- **Artifact budget scale** (`budget_scale.go`, [ADR-0076](../adr/0076-convergence-architecture.md) A). The orchestrator sets `BridgeRequest.BudgetScale > 1` for the build phase of a medium or large cycle; it stretches the artifact-wait budget. An unlisted agent scales from the driver's builtin `tmuxArtifactTimeoutS`, so the flag is exactly the default, stretched.
- **Model picker capture** (`capture_models.go`). `CaptureModelPicker` feeds modelquery's `RecipeLister`: send `/model` and Enter, poll up to six one-second ticks for a picker marker, send one extra Enter only while the picker is closed (codex's slash autocomplete swallows the first), and always finish with Esc. An ephemeral session is killed on a detached context. The live refresh passes a scratch `cfg.Workspace`, so escalation reports and ledger rows land outside the repo and are salvaged to `.evolve/models-probe`; `cfg.Worktree`, the session cwd, is deliberately left unset.
- **Catalog overlay** (`catalog_overlay.go`). `modelCatalogDirFn` resolves the catalog directory from policy's `bridge.catalog_dir`, else `.evolve`; `cmd/evolve` replaces it through `SetModelCatalogDirFn` rather than the environment. The parsed catalog is memoized per (dir, mtime) under a mutex.
- **CLI control adapter** (`clicontrol_adapter.go`). `cliController` is the production `clicontrol.Controller` and the one place the abstract `clicontrol.Event` becomes a concrete command: `Manifest.Control` maps the event, and `captureControl` boots or attaches the family's `*-tmux` REPL, sends the command and polls for the prompt marker. Each `Do` derives the family's config from a family-agnostic template (workspace, project root, bypass posture) through `RealizeFor`, so flags never bleed across CLIs. An unmapped event returns `ErrUnsupported` without booting. `captureControl` kills the session it created when it returns (`reapEphemeralSession`, also on a failed boot), unless the caller named the session; a kill that fails is named on stderr. Before 2026-10 every wave's usage probe left one live REPL per family on the loop's socket until the loop exited, because the orphan reaper skips sessions whose creator (the loop) is alive.
- **Billing snapshot** (`billing.go`). Operator tooling off the cycle path: snapshot the credential-resolution state (a hash of the credentials file's token prefix, `ANTHROPIC_API_KEY` presence, `ANTHROPIC_BASE_URL`) before and after a call and compare for an unintended auth path. File and env signals only ([ADR-0021](../adr/0021-agent-bridge-go-port.md)).
- **agy model tiers.** agy takes `--model "<display name>"`; `launchCmdLine` shell-quotes the display names ([cli-capability-matrix.md](../cli-capability-matrix.md)).
- **The pane states its authority and who the agent is** (`driver_tmux_prepare.go`, [ADR-0106](../adr/0106-logic-first-delivery.md) P3, T3). `stateAuthority` writes [`phaseidentity.Authority()`](internal-bridge-phaseidentity.md), the standing block that is the same on every dispatch, to the file the launch line names when the driver's manifest declares a system prompt channel (`system_prompt_file`: claude-tmux's `--append-system-prompt-file <workspace>/pane-authority.md`, set by `launchIntentFor` for a dispatch with an agent); the file is written atomically whenever the flag is realized, a boot-only pane included, so the CLI never launches naming a missing or half-written file. A CLI without the channel pastes the authority instead. Either way `prepareTmuxREPL` ends the bytes it writes to `resolved-prompt.txt` with the facts block, `phaseidentity.Block`, which states: the phase and cycle, the tmux session and the command that prints it, the two prompt files, the artifact the agent alone writes, and that operator-addressed instruction files are not about this pane. Only the driver knows the session, so the statement is finished here, after the engine's composed prompt, which stays a byte-identical prefix. A launch without an agent name or a pane appends nothing.
- **The pane shell carries the CLI's environment** (`driver_tmux_boot.go`, `driver_common.go`). A manifest's `default_env` is to variables what `default_args` is to flags: the realizer copies it into `Realization.Env`; a tmux driver sends one `export KEY=value` line per entry (sorted, the value shell-quoted) after `cd` and `EVOLVE_PROJECT_ROOT` and before the launch command, because a pane inherits the tmux server's environment, not the bridge's; a headless driver hands the same map to the process through `driverEnv`, under the request's `Deps.Env` overrides. Keys are validated as shell identifiers when the manifest is parsed, the loop's (`EVOLVE_`), the bridge's (`BRIDGE_`) and the credential variables are refused (the credential guards read the process environment before a launch and never see a manifest's map), and a value with a control byte is refused because it is typed into a pane. `claude-tmux` declares `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=false`: a suggestion is a background model request per turn and dim text under the input box that reads like agent output (cycle 1707 rendered "Yes, kill that session first." there). The recipe boot (`recipeSessionDriver.EnsureSession`, behind `CaptureModelPicker` and the recipe engine) sends the same export lines after its `cd` and before the launch, so a `/model` capture launches the CLI as a phase does. `agy-tmux` and `agy` declare `AGY_CLI_DISABLE_AUTO_UPDATE=1`, the off switch of agy's launch-time self-updater, so agy's version moves only at a loop boundary ([internal-cliupdate.md](internal-cliupdate.md)).

*File group 2: the `completion_*` and `contextfill_*` test families, `controllerfactory.go`, `coverage_batch2-7_test.go`, `delivery_failure_errhelper_test.go`, `doctor_test.go`, `driver.go` and the `driver_agytmux.go` / `driver_artifact_relocate_test.go` / `driver_claudetmux.go` / `driver_codex_test.go` / `driver_codextmux.go` / `driver_credentials_test.go` / `driver_inject_test.go` / `driver_liveness_routing_test.go` / `driver_model_token_test.go` family, plus their tests.*

- `newArtifactDetectorAt` (no baseline) and `newArtifactDetectorWithBaselineAt` (captured baseline) both exist because the existing debounce/finality suite writes files as harness setup for "agent wrote mid-session" scenarios, which is exactly what an absent baseline models; only the pre-dispatch-baseline tests construct with a captured baseline, the way production does before prompt delivery.
- Production captures the `dispatchBaseline` in `dispatchTmuxPrompt`, before prompt delivery, and the waiter threads it into the completion detector, the admission check and the idle nudge. It holds the (size, mtime) of every artifact candidate path that existed before dispatch and, under the `worktree-evidence` contract only, the worktree snapshot.
- After the wait loop's context is cancelled (orchestrator timeout, SIGTERM, the next phase tearing the session down), it takes one final completion poll before giving up, so a session that finished at the buzzer is not laundered into a timeout; that final poll runs with the already-cancelled context. Tests for this drive the real production wait loop via `Engine.LaunchArgs` rather than polling a `completionDetector` in isolation, because the wait loop itself is the fault site, not the detector.
- **The `worktree-evidence` completion contract** (`completion_worktree.go`, [ADR-0113](../adr/0113-correction-completes-on-worktree-evidence.md)) is the artifact contract plus one door at the idle review checkpoint, for a correction re-dispatch of a source-writing phase (core decides who qualifies: `core.PhaseRequest.BridgeCompletion`, projected by the phase runner onto `BridgeRequest.Completion`). `dispatchTmuxPrompt` takes a `git --no-optional-locks status --porcelain=v1 -z --untracked-files=all --no-renames` snapshot of the worktree (size and mtime per listed path) beside the artifact baseline, before the prompt goes out. When a checkpoint pauses on a pane that is not busy, `replWaiter.completeOnIdle` asks the detector through the optional `idleCompleter` interface; `worktreeEvidenceDetector` completes when the located deliverable still matches its pre-dispatch baseline, every secondary exists, and a second snapshot differs from the first on at least one path that is not host-owned (`.evolve/`, the workspace, the deliverable's own candidate locations). The waiter logs the note naming the carried deliverable and the changed paths and emits `BRIDGE_COMPLETED_ON_WORKTREE_EVIDENCE`. The bridge judges only evidence; the runner's verify and core's review gate judge the deliverable.
- The contract names are declared once, as the typed `core.CompletionContract` constants (`artifact`, `stdout`, `git`, `worktree-evidence`) beside `BridgeRequest.Completion` in `core/ports.go`. The bridge aliases them (`completionArtifact` and the rest), `Config.Completion` carries the same type, and `parseLaunchArgs`' `--completion` string is converted once where `Config` is built. `completionContractName` maps `""` to the artifact contract and leaves every other mode its own name (an unrecognized mode keeps its own bytes rather than being renamed). The names are the Strategy pattern's dispatch keys — the detector `newCompletionDetector` builds for a name is the detector the name promises. Only the tmux drivers honour a contract; the headless drivers ignore it.
