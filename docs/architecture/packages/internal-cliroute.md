# internal/cliroute

> **Isolation ([ADR-0154](../adr/0154-the-pipeline-is-the-only-controller-and-each-agent-is-an-isolated-replaceable-worker.md)).** The routing table holds the family floors and the defaults of the flow seats as data (I-6). The spec of record: [llm-isolation.md](../llm-isolation.md).

> The design and its landing plan: [cli-routing-table-2026-10.md](../../plans/cli-routing-table-2026-10.md). The plan primitives this package composes: [internal-llmroute.md](internal-llmroute.md). The schema of the `cli_routing` block: [internal-policy.md](internal-policy.md). The Claude-family floor list and `cross_family_with`: [internal-profiles.md](internal-profiles.md). This page keeps the package-level detail those do not.

## Purpose

`internal/cliroute` is the one routing table and the one resolver for every launch path. The operator declares in `.evolve/policy.json` which CLIs exist, which CLI does each kind of work, and what happens when a chain runs out (the `cli_routing` block). `Compile` turns that block into a `Table` and reports every integrity finding at once. `Router.Resolve` turns one launch request into a dispatch `llmroute.Plan`. When the block is absent, `Resolve` reproduces today's resolution byte for byte (the legacy projection), so wiring a launch path through it changes nothing until the operator writes the block.

Status: L1a (2026-10-05) built and tested the resolver unwired. **L1b (2026-10-06) wires every launch path through it** ([ADR-0119](../adr/0119-one-routing-table-one-resolver.md)); see [Wiring](#wiring-l1b-2026-10-06). The checked-in policy has no `cli_routing` block, so every launch still resolves through the legacy projection; the operator's table lands in L2.

## Design

- **Strategy: two resolvers behind one call.** A declared table runs the declared pipeline; an absent block runs the legacy projection. The caller never branches.
- **Pipeline: the declared resolve is a list of stages.** Each stage is a function of under 50 lines that takes and returns a `resolution` value. The first stages are: rule → the agent's `model` → the headroom order (W4) → guarded env → caller CLI → advisor CLI → advisor tier. The last stages are: ladder effort → probe → bench → `after_chain` → the tier ceiling. A stage that refuses returns an error naming the agent; a stage that drops or ignores an input appends a `Trace` line.
- **Pipeline: the declared resolve is a list of stages.** Each stage is a function of under 50 lines that takes and returns a `resolution` value. The first stages are: rule → the agent's `model` → the headroom order (W4) → guarded env → caller CLI → advisor CLI → advisor tier. The last stages are: ladder rung → probe → bench → `after_chain` → the tier ceiling. A stage that refuses returns an error naming the agent; a stage that drops or ignores an input appends a `Trace` line.
- **The pin is the base rung (ADR-0142 L4, plan D7).** `agents.<agent>.model` fixes the tier of the first try, and `overlayTier` keeps an advisor tier off it. The stage `applyLadder` runs after `overlayTier` and applies the ladder rung: `Overlay.LadderTier` and `Overlay.Effort`. It ignores `modelFixed`, so a ladder rung of deep raises a pinned balanced builder to deep.
  - `clampLadder` bounds the rung by `agents.<agent>.max_tier` and `max_effort`. An unset bound resolves through `retryladder.Bounds.Resolved` to deep and high. A clamp adds a trace line, for example `ladder tier top clamped to max_tier deep`.
  - The ladder never goes below the base (`Table.ladderBase`). The base tier is the tier of the plan before the rung. The base effort is the effort of the table for that tier and agent. A rung below the base is raised to it. A bound below the base holds the rung at the base, so a builder pinned at top and xhigh keeps top and xhigh. The decider of L2 also never drops below the base effort.
  - A rung that is not a tier or an effort level refuses the resolve.
  - The base effort comes from the same lookup as `Router.Effort`, so the floor matches the launch effort. A base or a bound that is not a level (a literal model id) sets no floor or no ceiling.
  - The rung changes only the tier and the effort. The chain, the allowed set and the Claude family floor stay, and the tier ceiling still runs after it.
  - The legacy path clamps the rung by the default bounds and puts the clamp lines first in the trace. A legacy pin keeps the ladder off, as it keeps every overlay off.
  - A bound on a phase alias (`agents.build`) bounds its agent, like `model`.
  - `compileLadderBounds` refuses an unknown `max_tier` or `max_effort` (error findings on `.max_tier` and `.max_effort`), so `evolve cli-routing set` refuses them before the write. A rule that sets only an effort or bounds has no chain of its own (`inheritsChain`).
  - Pinned by `TestResolve_ThePinIsTheBaseRungAndOnlyTheLadderRaisesIt`, `TestResolve_ALadderRungAboveTheBoundsIsClampedAndReported`, `TestResolve_UnsetLadderBoundsAreDeepAndHigh`, `TestResolve_AnExplicitBoundLetsTheLadderReachIt`, `TestResolve_AFamilyFloorSeatStaysOnItsFloorWhenTheLadderRaisesIt`, `TestResolve_TheLegacyPathRaisesToTheLadderRungWithinTheDefaultBounds`, `TestResolve_ALegacyPinKeepsTheLadderOff`, `TestResolve_TheLadderNeverGoesBelowThePin`, `TestResolve_ABoundBelowThePinHoldsTheRungAtThePin`, `TestResolve_ALadderRungThatIsNotATierOrAnEffortIsRefused`, `TestResolve_TheLegacyPathRefusesALadderRungThatIsNotATier`, `TestClampStep_AnUnknownBaseOrBoundSetsNoFloorAndNoCeiling`, `TestResolve_ABoundOnAPhaseAliasBoundsItsAgent`, `TestCompile_AnUnknownLadderBoundIsAFinding`, `TestCompile_ABoundsOnlyRuleNeedsNoChain`, `TestResolve_ALadderEffortReachesThePlanBesideAnAgentModel`, `TestResolve_TheLegacyPathCarriesALadderEffort` and `TestResolve_ALegacyPinKeepsTheLadderEffortOff`.
- **Builder: `Compile` accumulates findings** instead of stopping at the first. Each finding is recorded once, so an agent that serves two roles under one bad rule is reported once.
- **One rule predicate.** `Table.selectRule(agent, role selection, profile, allowed)` picks the rule, filters its chain by the allowed set and returns either the selection or a `RuleError`. `Compile` and `Resolve` both call it, so the check that a launch can run and the check that the table is valid are one function.
- **Profiles are snapshotted at `Compile`.** `Compile` lists the profiles and loads each once; `Resolve` never reads them again. In declared mode a listed profile that failed to load is an error from `Resolve` (and a `profiles.<agent>` finding), never a nil profile, because a nil profile would widen the allowed set to every CLI in `clis`. The legacy projection keeps today's behaviour: an unloadable profile resolves as no profile, as the bridge chain does now. An agent with no profile at all resolves with no profile restriction in both modes. A profile minted after `Compile` is not seen until the table is compiled again (an L1b decision in the plan).
- **Rule precedence.** `agents.<agent>` > `work.<role>` > `default` > the profile's own `cli` + `cli_fallback`. The role is `phasespec.PhaseSpec.RoleOrDefault()` of the request's phase, looked up through `phasecontract.RegistryKey` (so the runner's `retro` finds the registry's `retrospective`) and inferred from the name when the catalog lacks it. A request with no phase (a bridge-chain launch) takes the agent's role when every phase the agent serves has the same role (retrospective: `retro` and `retrospective`, both control), and otherwise has no role, so `work` does not apply. `Compile` checks every selection `Resolve` can make: each role of the agent's phases, plus the no-role selection whenever the agent serves no phase or phases of several roles.
- **Agent keys accept a phase name.** `agents.audit` normalizes to `auditor`. A profile name is taken as is. A phase name maps through the catalog alone: `PhaseSpec.AgentName()` of the `phasecontract.RegistryKey` phase, without the `evolve-` prefix (`go/internal/cliroute/compile.go:206`). The phase registry sets `agent` for `tdd`, `build` and `audit` (`evolve-tdd-engineer`, `evolve-builder`, `evolve-auditor`), so no second phase-to-agent table exists (cycle 1866). Without a catalog, a phase key that is not a profile is refused as neither; only the per-launch router compiles without a catalog, and it refuses a declared table (`RefuseLaunchRouter`).
- **The allowed set.** `A(agent) = clis ∩ profile.allowed_clis ∩ ({claude} for a floor agent)`, in `clis` order. The profile part is `(*profiles.Profile).AllowsFamily`, the floor part `profiles.IsClaudeFamilyFloor`. Chains from `default`, `work` and the profile rule are filtered by `A` silently (a `Trace` line); an `agents` entry outside `A`, or a chain left empty, is an error from `Resolve` and a finding from `Compile`.
- **An assignment is a chain, not a lock.** Every rule keeps the probe, the bench and `after_chain`. `after_chain: other_clis` (the default) appends the rest of the allowed set `A`, which is already `clis` in their listed order, through `llmroute.ApplyUniversalFallback`; `stop` appends nothing. Building the tail from `A` means no later filter is needed.
- **The advisor overlay applies per dimension.** A table rule (`agents`, `work` or `default`) fixes the CLI chain, so the advisor's CLI is ignored and traced; under the profile rule it is promoted when it is inside `A`. The advisor may still raise the tier unless `agents.<agent>.model` sets one. A per-run `EVOLVE_<AGENT>_MODEL` outranks `agents.<agent>.model`.
- **Env and caller primaries.** `EVOLVE_<AGENT>_CLI` and `EVOLVE_CLI` stay per-run overrides, but a value outside `A` is an error naming the key. A `CallerCLI` (today's `bridgechain.leadWith`) applies only under the profile rule and only inside `A`; otherwise it is ignored and traced.
- **The tool-use filter.** A worktree phase needs a CLI with tool use. After the universal tail, the declared pipeline and the legacy projection both call `requireToolUse` (`tool_use.go`). It runs only when `Request.NeedsTools` is set. It calls `llmroute.DropToolless` with `Host.Toolless`. It removes a toolless CLI whoever named it: the profile, an env override, the advisor, a pin or the caller.
  - Both paths record a note in `Trace`: the dropped CLIs, or that the host does not judge tool use. The runner prints the `Trace` lines, so the filter is never silent.
  - If no candidate remains, `Resolve` returns a `ToolUseError` that names the rule and each dropped CLI.
  - The host flags a CLI only on proof. A CLI whose manifest does not load stays in the chain, and the launch reports the load error.
- **The tier ceiling rides the plan.** `tiers.<tier>` becomes `Plan.TierCeiling` (tier → families), and `llmroute.DispatchTiered` skips every (CLI, tier) attempt the ceiling excludes, including the `after_chain` tail. With `tiers.deep = [claude]`, (agy, deep) is never launched; a walled Claude at deep steps down the existing tier chain and may run agy at balanced. `Resolve` refuses a plan in which no (CLI, tier) pair is permitted at all, checking `Plan.Tiers`, or `Plan.Model` when `Tiers` is empty, exactly as the walk does. `Compile` runs the same predicate on each selection's static plan: the selected chain plus the `after_chain` tail unless `stop` (built by the same `Table.withAfterChain` that `Resolve` uses), all inside `A`, at each tier chain the configuration can produce. Those are the chain of `agents.<agent>.model` when it is set, because it fixes the tier; otherwise the chain of the profile's default tier (an unset default dispatches as balanced) and of each `model_tier_overrides` tier. Each tier chain comes from `llmroute.ApplySoftOverlay`, the code path `Resolve` takes, so the envelope floor applies alike. A per-run `EVOLVE_<AGENT>_MODEL` or an advisor tier can still reach a tier no configuration names; that refusal stays `Resolve`'s alone. The plan carries a deep copy of the ceiling. The tier names are `policy.TierNames()`, the one ordered vocabulary.
- **The legacy projection reproduces both of today's resolvers.** For a request with a phase it is the runner's `resolveDispatchPlan`: the phase-keyed pin (validated with `policy.ValidatePin`, the runner's own error), `llmroute.Resolve`, the advisor overlay unless pinned, then — unless a pin fixes the CLI — the probe, the bench and the universal tail (`workflow.universal_fallback`, with `universal_fallback_exclude` applied to `Host.Discover`). For a request with no phase it is `bridgechain.DefaultPlanResolver`: no pin, `CallerCLI` leading, probe, bench, tail. `leadWith` is that resolver's helper, moved here; L1b deletes the original.
- **Imports.** `policy`, `profiles`, `phasespec`, `phasecontract`, `llmroute` and `envchain`. Never `core` or `bridge`: the bench and the tool-capability check arrive as seams, so the runner and the bridge chain can import this package.

## Wiring (L1b, 2026-10-06)

One Router per process, compiled once at each composition root by `cmd/evolve/cli_routing_root.go` (`buildCLIRouter`: the policy, the merged phase catalog, `routingProfilesDir(projectRoot)` = `<project>/.evolve/profiles`, the one profiles directory every root compiles and the one the runner has always read its profile from, `WithToolCapable(bridge.HasToolUse)`, and the production `Host` from `routingHost(log, now)`: `exec.LookPath`, the cli-health bench on the injected clock, and the raw doctor discovery memoized for the process). `TestProductionRouter_ReplaysTheLegacyGolden` (`cmd/evolve`) replays the whole golden through exactly this composition, with a fake doctor report that includes a banned family (agy under the compiled-default ban), a toolless driver (ollama) and a blocked one; `TestOneProfilesDirectory_ThePreflightAndTheCycleCompileTheSameTable` pins that `evolve cycle run` and the loop preflight compile the same table when `--evolve-dir` and the plugin root differ from the project. A malformed policy or any error finding exits 2 before the first dispatch (`exitRoutingRefused`).

## L2 additions (2026-10-07)

- **`Decision.WalkAt(tier, benched)`** returns the advisor's walk: the decision's candidates the ceiling permits at `tier`, with the first unbenched one leading, and the decision's triggers. Nothing permitted is a refusal wrapping `ErrRefused`. The root's `resolveRouterDispatchHealthy` reads its `{cli, model, healthy}` from it, so the advisor golden is unchanged. Pinned by `TestDecision_WalkAt_*`.
- **`Decision.Walk()`** (2026-10-07, the L2 fix round) is `WalkAt` at the decision's own tier with nothing benched: the CLI a single-launch caller names. The retro's launch, contract escalation (its dispatch CLI, the family it escapes and its candidates) and `Router.ResolveRole` read `walk.Candidates[0]` instead of `Plan.Candidates[0]`, because at deep the ceiling can drop the plan's first CLI, and the overlays and the logged CLI must match what runs. Pinned by `TestDecision_Walk_IsWhatTheCeilingPermitsAtTheDecisionsOwnTier`, `TestResolveRole_ADeepRoleReportsTheFirstCLITheCeilingPermits`, `TestRetro_ADeepRetroLaunchesTheFirstCLITheCeilingPermits` and `TestContractEscalation_ADeepDispatchNamesAndEscalatesOnlyWhatTheCeilingPermits`.
- **Every decision owns its triggers.** A `Decision`'s `Plan.Triggers` is a private copy, so a caller that edits or appends through one decision's triggers never changes the next decision's or the package default. Pinned by `TestRouter_EveryDecisionOwnsItsTriggers` (dispatch and advisor launches), which replaced cycle 1821's predicate 003 when exit 87 joined the default set (the archive is `docs/private/research/archived-2026-10-07/superseded-predicates/`).
- **A trigger list without 87 is a warning** (2026-10-07). `Compile`, in the legacy projection and under a declared table alike, warns `profiles.<agent>.cli_fallback_on_exit` when a profile's own list omits `llmroute.ExitModelMismatch`: a target that boots another model family would then end the walk instead of handing the attempt to the next CLI. A profile with no list takes the default set, which has 87. Pinned by `TestCompile_WarnsWhenAProfilesTriggerListOmitsTheModelMismatchExit`.
- **`Setup.Bypass`** builds a router whose every answer comes from the bypass table, so a `--bypass-policy` run cannot leak the declared table through a launch path that does not set `Request.BypassPolicy`. Pinned by `TestBuild_ABypassRunAnswersEveryRequestFromTheBypassTable` and `TestBuild_ANormalRunStillRoutesTheTable`.
- **`RefuseLaunchRouter(pol)`** refuses (`ErrRefused` wrapping `ErrNoRootRouter`) when a per-launch router would route a declared table on its own. **`NewLegacyLaunchRouter(projectRoot, sp)`** is the one per-launch router the retro and contract escalation build: it loads the project's policy, refuses a declared table, and otherwise routes the empty policy as before.
- **The profile-less finding.** A declared table with no `default` gets a `cli_routing.default` warning, because only `default` reaches the model classifier and an agent no profile names. Pinned by `TestCompile_ATableWithNoDefaultWarnsThatEveryProfileLessLaunchIsUnreachable`.

| `cli_routing.agents.<key>.order` | error | a value other than `headroom`; `headroom` on a rule with no `cli` |
| `cli_routing.agents.<key>.headroom_pct` | error | set without `order: headroom`; a value outside 1 to 100 (0 or absent means 60) |
| `cross_family_with.<a>+<b>` | warn | one agent of the pair has `order: headroom`, and its chain holds the first family of the other agent. This warning replaces the static first-family check of that pair. |
| `agent.<agent>` | error | the agent's chain is empty after the allowed-set filter, for any selection `Resolve` can make: each role of its phases, and the no-role selection when a phase-less launch has no single role |
| `cross_family_with.<a>+<b>` | error, or warn | the two resolved primaries share a family: an error when `clis` has two or more families, a warning on a Claude-only install; a warning when only their fallbacks share a family |
| `pins`, `workflow.universal_fallback`, `workflow.universal_fallback_exclude`, `router.cli`, `router.model`, `router.plan_model`, `router.propose_model` | error | set together with the block (two sources); the message points to `evolve cli-routing migrate`. The per-decision models were added in the L1b fix round (2026-10-06): the advisor root lays them over the decision's model, so beside a table they would swap the tier the table and its ceiling chose |
| `profiles` | error, or warn | no profile source, or the list fails: an error in declared mode, since an empty snapshot would silently route every agent as profile-less. With no block, a profiles directory that does not exist is a warning and an empty snapshot, which is how the runner and the bridge chain treated it before L1b (fix round, 2026-10-06); any other list failure stays an error. |
| `profiles.<agent>` | error | a listed profile does not load (declared mode) |

An unknown key inside the block, or a `null` block or agent rule, is not a finding: `policy.Load` refuses the file (strict decode, see internal-policy.md).

## The tier share (ADR-0150, 2026-10-21)

> Spec of record: [deep-tier-share.md](../deep-tier-share.md). Plan: [deep-tier-share-2026-10](../../plans/deep-tier-share-2026-10.md).

- `cli_routing.tiers.<tier>.share_pct` (1 to 99) gives the first family of the tier chain that percent of the seats at the tier. `compileShares` refuses a value outside 1 to 99, a tier with no `clis`, and a chain of one family. The key of each finding is `cli_routing.tiers.<tier>.share_pct`.
- The stage `shareTier` runs after `applyLadder`. When the chain starts with the shared family, it hashes `<cycle>|<agent>|<phase>` into a bucket from 0 to 99 (`shareBucket`, FNV-1a). `Request.Cycle` carries the cycle from the runner and the bridge chain.
- A bucket below the share keeps the seat. Otherwise, or when the family is paced, `lastFamily` moves the shared family to the end of the chain. The walk keeps it as a fallback.
- The pace reads `Host.TierWeek` (production: `projectTierWeek` in `cmd/evolve`) and `Host.Now`. A family is paced when its week window is used faster than the week goes. A missing reader, a read error, no window or no reset time leave only the share, and the trace says why.
- An explicit pin wins over the share (`sharePin`). The stage skips the share when an env override leads the chain. It also skips the share when the caller CLI or the advisor CLI of a profile-rule agent is in the shared family. The trace names the pin.
- `Router.ShareNotes(projectRoot, chain)` gives one `share:` note for each shared tier whose family is in the chain. `evolve cli-routing explain` prints it.
- Pinned by the `TestShare_*` tests in `share_test.go`, `TestShareNotes_NameEachSharedTierAndItsPace`, `TestCompile_AShareNeedsATierChainAndAPercentInRange` and `TestShareBucket_TheBucketsOfTheSpecExample`.

## The headroom order (W4, 2026-10-19)

> Plan: [wave-latency-2026-10](../../plans/wave-latency-2026-10.md) D4 and W4. Research: [wave-latency-2026-10](../../research/wave-latency-2026-10.md) F3.3, F3.5, O8 and O9. The measure: [internal-lanetime.md](internal-lanetime.md). The week use: [internal-usageprobe.md](internal-usageprobe.md).

An agent rule can sort its chain by quota headroom and by the measured lane time to a PASS of each family. The rule is policy data: `cli_routing.agents.<agent>.order: "headroom"`, with `headroom_pct` (`DefaultHeadroomPct`, 60, when absent or 0). A rule without `order` routes as before, and the stage reads no port.

**Example.** `.evolve/usage-windows.json` of 2026-10-19 records the week windows claude 15%, agy 100% and agy-claude 100%. W0 has no measure yet. With `headroom_pct` 60, the chain `agy, agy-claude, claude` becomes `claude, agy, agy-claude`: claude has headroom, and agy and agy-claude go to the tail in the order without a measure.

The stage `orderByHeadroom` (`headroom.go`) runs after `fixAgentModel` and before `guardEnv`:

1. It reads `Host.WeekUsed(projectRoot)`: the percent used of the family week window of each family. With no port, a failed read, or no family of the chain in the read, the policy order stays. The stage logs that and adds a `Trace` line.
2. It reads `Host.LaneTimes(projectRoot)`: the `[]lanetime.FamilyLane` of the last wave boundary. A failed read means no measure. The stage logs that and adds a `Trace` line.
3. It sorts the chain, stable, on three keys. First, a family at or above `headroom_pct` goes after the families below it. Then a family with a measure (`PerPass` above 0) goes first, the shorter `PerPass` first. Last, the order without a measure is claude, agy, agy-claude. Another family keeps its policy place after these.
4. It adds two `Trace` lines: the week use of each family and the measure of each family. `evolve cli-routing explain <agent>` prints them as `note:` lines.

The stage moves a family and never removes one. The probe, the cli-health bench, `after_chain` and the tier ceiling run after it as before. Thus a quota exit still puts the family in its cooldown, and the bench demotes it again (`TestHeadroom_TheCliHealthBenchStillDemotesAFamilyInCooldown`). An env override still leads, because `guardEnv` runs after this stage. The caller CLI and the advisor CLI do not apply to an `agents` rule, as before.

**The seam.** Each cycle of a wave is its own `evolve cycle` process (`execCycleLaunch`, `cmd/evolve/cmd_fleet.go`), and each process compiles its own router. A measure at router build thus reads the run history once for each cycle. Instead, the parent loop computes the measure once for each wave: `runPreWaveProbes` (`cmd/evolve/cli_usage_probe.go`) calls `recordLaneTimes`, which writes `LaneTimeToPass(ReadCycles(evolveDir, 0, 0), DefaultBuilds)` to `.evolve/lane-time.json`. The production `routingHost` reads that file (`projectLaneTimes`) and the usage windows that the pre-wave usage probe recorded (`usageprobe.WeekUsed`). This package makes no network call, no tmux call and no read of the run dirs.

| Design | Rejected because |
|---|---|
| Compute the measure in `wireCLIRouter` | Each cycle is a process, so this reads the whole history once for each dispatch. |
| Pass the measure to each lane in an env var | The usage probe already shares its cache through a file in `.evolve`. One more file keeps one pattern. |
| Remove a family at the limit from the chain | The family is then not a fallback. The plan asks only that it leaves the head (§6 W4). |

**The cross-family pair.** The auditor and the tdd engineer have `cross_family_with: builder` and run on claude only. A builder rule with `order: headroom` and claude in its chain starts on claude while claude has headroom. The static first-family check reads the policy order, so it cannot see this. Thus `Compile` gives a `cross_family_with.<a>+<b>` warning for each such pair, and `evolve cli-routing check` and `explain` print it. An error is rejected: claude is in each builder chain, so the rule never compiles with it.

The order without a measure is the plan value (D4), not the order of the `cli` list. The `cli` list keeps its role as the order of the other families and as the order when the usage read fails.

Limits:

- The routing host reads `<project>/.evolve`, the same directory as the policy. A loop with `--evolve-dir` writes the files to another directory, so the order fails open there.
- The usage file keeps one observation for each CLI. A failed usage query replaces the last good one, and the families of that CLI then count as families with headroom.
- The week use is as old as the last pre-wave usage probe (`cli_health.proactive_probe`). A window whose reset has passed does not count.
- A family with no week window in the file counts as a family with headroom.
- The measure compares different tasks, so it is an estimate (F3.3).
- `evolve cli-routing set` keeps the order keys of a rule, but it cannot write them yet.

Tests (`headroom_test.go`): `TestHeadroom_WithTheWeekAt14PercentAndNoMeasureTheBuildStartsOnClaude`, `TestHeadroom_AFamilyAtTheLimitLeavesTheHead`, `TestHeadroom_WithAMeasureTheShorterLaneTimeToAPassGoesFirst`, `TestHeadroom_AFailedUsageReadKeepsThePolicyOrder`, `TestHeadroom_ASeatWithoutTheOrderKeyRoutesAsBefore` and `TestCompile_TheOrderKeysAreChecked`. Without an order key, every tracked agent resolves the same with and without the ports, and no port is read.

## Findings

- **2026-10-05, building the golden.** Today's resolvers let per-run and advisor inputs cross `allowed_clis`: the advisor overlay `{cli: agy, tier: deep}` puts `agy-tmux` first on the builder's chain although `builder.json` allows only claude and codex, and `EVOLVE_BUILDER_CLI=agy-tmux` does the same. The bridge-chain resolver ignores policy pins and the advisor overlay altogether. The declared mode refuses or ignores each of these; the legacy projection keeps them, by design, until L2.
- **2026-10-05, the operator's table needs the builder edit.** Compiled against the tracked profiles, `{clis: [agy, claude], default: [agy, claude], tiers: {deep: [claude], top: [claude]}}` reports `cross_family_with.auditor+builder` as an error: `builder.json` does not allow agy, so the builder's chain collapses onto claude, the auditor's family. With `allowed_clis` widened to agy (L2), only the accepted warning remains (the two share claude as a fallback). `TestCompile_TheOperatorTableCollapsesTheBuilderOntoTheAuditorWithoutTheL2BuilderEdit` pins both halves. L2 (2026-10-07) made the edit (`builder.json` and `tester.json` allow `[agy, agy-claude, claude, codex]`), so the checked-in table compiles with only the two accepted fallback warnings and `TestCompile_TheOperatorTableCollapsesTheBuilderOntoTheAuditorWithoutTheL2BuilderEdit` is retired.
- **2026-10-05, review round 1.** The architecture review found four gaps, now closed and pinned by tests that fail on a mutant of each fix. A walk the ceiling empties reported itself walled although no wall was known. A phase-less launch could take a different chain from the same agent's phase launch with no `Compile` finding (the tester and the retrospective). `Resolve` re-read profiles and silently widened an unloadable one to every CLI. And a `null` block decoded as the legacy sources. The reviewers' probes and mutants are recorded in the plan's L1a landing notes.
- **2026-10-05, review round 2.** The re-review confirmed round 1 and found one more gap of the same class. Under `{clis: [agy, claude], default: [agy], tiers: {deep: [claude], top: [claude]}, after_chain: stop}`, `Resolve` refused `intent` (its envelope pins it to deep, so its tier chain is `[deep]` alone) while `Compile` reported nothing. Under L1b that table would have passed `check` and the start gate, then failed mid-cycle. The ceiling refusal is now the typed `CeilingError`, and `Compile` runs it on every selection's static plan.
- **2026-10-18, the tool-use filter (inbox `capability-filter-at-plan-resolution`).** The request: "every dispatch chain drops a CLI without tool use at plan resolution, whatever named it". The wave-24 P0 made the universal tail hold only CLIs with tool use (`cmd/evolve/universal_fallback_tail.go:14`). Five other sources can still put `ollama-tmux` into the chain of a worktree phase.
  - The sources are the profile `cli` or `cli_fallback`, an `EVOLVE_*` CLI override, the advisor overlay, a policy pin and the caller CLI.
  - No tracked profile names ollama, so the defect is latent.

  **F1.** The `ollama-tmux` driver refuses a worktree phase with exit 10 (`go/internal/bridge/driver_ollamatmux.go:30`). Exit 10 is not a walk trigger (`go/internal/llmroute/llmroute.go:19`).
  *Implication:* the walk ends on the refusal, and the cycle fails.

  **F2.** `Compile` rejects a toolless driver in `clis` and in each declared chain (`go/internal/cliroute/compile.go:108`). It never sees a value that arrives with a request. On the legacy projection, nothing else filters those values.
  *Implication:* a declared table is safe by construction, and the legacy projection is not. The legacy projection serves `--bypass-policy`, a project with no table and every per-launch router.

  **F3.** `HasToolUse` is `err == nil && !m.Toolless` (`go/internal/bridge/tool_use.go:3`). A manifest that does not load reads as no tool use. A corrupt override in `bridgeManifestDir`, a broken `base` and a broken `model_tier_map_from` all make a manifest fail to load.
  *Implication:* a filter built on `HasToolUse` drops a live driver and hides the manifest fault behind a tool-use verdict.

  | Id | Decision | Because | Rejected options and why |
  |---|---|---|---|
  | D1 | Drop the CLI in the resolver, on the final chain, and only when `Request.NeedsTools` is set. | F1, F2 | Filter in the runner and in the bridge handle: that makes two copies of one rule, and `TestOnlyCliRouteBuildsChains` keeps chain building in `internal/cliroute`. |
  | D2 | `NeedsTools` is `Worktree != ""` in `routeRequest` and in `DefaultPlanResolver`. | F1 | Drop the CLI for every phase: the driver accepts a phase with no worktree, so the drop removes a CLI that can run it. |
  | D3 | The predicate is the `Host.Toolless` seam. `routingHost` and the launch router of the runner pass `bridge.LacksToolUse`. | F2 | Reuse the `WithToolCapable` compile option: `NewSingleProfileRouter` takes no compile option, and its `newSingleProfileRouter` seam in `internal/subagent` has a fixed type. |
  | D4 | An empty chain is a `ToolUseError` inside `ErrRefused`. | F1 | Make exit 10 a walk trigger: it reroutes any bad-flags failure of any CLI, and a non-trigger exit must stop the walk. |
  | D5 | Drop a CLI only when its manifest loads and says `toolless` (`bridge.LacksToolUse`). A CLI whose manifest does not load stays in the chain. | F3 | Drop on `!HasToolUse`: it drops a live driver for a corrupt override, and the error hides the real fault. Carry the load error in `ToolUseError`: the walk still reroutes a live driver, and the load error shows only when every candidate drops. |

  *Consequences.*
  - A declared production table never reaches the stage with a toolless CLI, because `WithToolCapable` makes it a compile error. The stage guards a table compiled without that option.
  - The refusal of the stage is not a `Compile` finding, because `Compile` has no request.
  - A CLI that the host does not flag stays in the chain. A driver whose manifest does not load reaches the launch, which reports the real load error. The cost is one failed launch of that driver, which is the behavior without the filter.
  - A `Host` with no `Toolless` filters nothing and records that in `Trace`.
  - The filter costs one manifest read for each candidate on a worktree resolve.
  - `retro` and the contract escalation resolve a route without a launch request, so they do not set `NeedsTools`. This change leaves them as they were.

  *Proof.* With `DropToolless` stubbed to return its input, the `llmroute`, `cliroute`, runner, bridge-chain and `cmd/evolve` tests fail. With the `NeedsTools` and `Toolless` lines removed, the wiring tests fail. With `LacksToolUse` stubbed as `!HasToolUse`, `TestLacksToolUse_AnUnloadableManifestIsNoEvidenceOfNoToolUse` fails. The wiring tests are `TestResolveDispatchPlan_AWorktreePhaseDropsACLIWithoutToolUseWhoeverNamedIt`, `TestDefaultPlanResolver_AWorktreeLaunchDropsACLIWithoutToolUseWhoeverNamedIt` and `TestBuildCLIRouter_AWorktreePhaseOfTheRootRouterNeverWalksOntoACLIWithoutToolUse`.
