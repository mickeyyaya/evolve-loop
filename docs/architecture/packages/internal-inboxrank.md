## Purpose

`internal/inboxrank` turns the facts of pending inbox items into one explainable priority order. `Score` computes an item's `Breakdown`: one `Term` per factor (its normalized value, its policy weight and their product) and the `Facts` behind them. `Order` scores a list and sorts it with a total tie-break. It is pure: no file is read or written, the clock and the recurrence counts are inputs (`Context.Now`, `Context.Recurrence`), and the weights come from `policy.InboxPriorityConfig`. It imports `inboxbatch` and `policy` only: `go list -deps ./internal/inboxrank` names no `internal/recurrence`, because the caller turns the ledger into counts. P1 (2026-10-06) shipped it unwired, with `evolve inbox rank` as its only caller. Since P2 (the same day) it is the one order every inbox consumer reads:

| Consumer | How it reads the rank |
|---|---|
| The wave seed, the widen and the launch refill | `triagecap.ReadInboxBacklog` returns the lane-ready backlog in `Inputs.Order`; the selectors keep that order |
| The triage prompt's `inbox_batches` menu | `inboxbatch.Classify` with `Config.Order: Sequence(ranked)`, rendered with `Labels(ranked)` |
| `evolve inbox batches` | the same composition as the triage prompt |
| `evolve inbox rank` | `Inputs.Order` per lane-menu list |
| The dashboard's inbox queue | `Inputs.Order` over every pending item |

Each consumer loads its `Inputs` through `rankinputs.Load(evolveDir, now)`, and no other code orders inbox items by weight (the guard below).

## Design

- **A weighted sum of normalized features.** Each of `base`, `class`, `unblocks`, `recurrence`, `age` and `goal` is mapped to [0, 1] and multiplied by its policy factor; the score is the sum, in that fixed order. The definitions and the reasons for the default factors are ADR-0121's. A sum keeps every input able to move an item and makes the explanation additive: `--explain` prints exactly the terms the score adds.
- **One factor vocabulary.** `Factors()` returns the six factors in score order, as a fresh slice. A `Breakdown`'s terms come in that order (`TestScore_ContributionsAddUpToTheScore`), and `evolve inbox rank` prints its table header from it, so the header and the rows cannot disagree. The policy package names the same factors as JSON keys and validates them by index (`inboxFactorNames` beside `InboxPriorityFactors.weights()`); it cannot import this package, so `TestFactors_AreThePolicysFactorNamesInItsOwnOrder` pins the policy side from here: a factors block naming none must list the names in `Factors()` order, a negative weight under each key must be refused under that key's name, and a weight of 1 under each key alone must reach that factor's term and no other.
- **Normalization never depends on other items' scores.** `unblocks` and `recurrence` are capped counts (`min(n, cap) / cap`), not ratios to the queue's maximum, so filing one item never changes another's score except through the item's own dependents. `class` is `(n − i) / n`, so the last class still scores above an unknown one (0). A negative count from the recurrence seam counts as 0, so a bad seam cannot pull a score down. `age` is a half-life curve, 0 for an undated or future-dated item, since `inboxbatch.Item.FiledAt` never guesses a date.
- **`unblocks` walks the whole queue.** `Context.Queue` is every pending item, not the list being ordered: a ready item's dependents are usually on the waiting list. The walk is a breadth-first search over a reverse-deps index with a seen set, so a dependency cycle or a repeated dep counts each dependent once and never the item itself.
- **One class position.** `Facts.ClassPosition` is the item's index in `class_order`, -1 when the order lacks its class, computed once per score through `inboxbatch.PriorityClassPosition`, the membership rule `inboxbatch.CheckPriorityClass` validates with. The class feature, `Facts.ClassKnown()` and the verb's "`i` of `n` in class_order" all derive from it (`TestScore_TheClassPositionIsTheOneFactBehindTheClassFeature`). The JSON carries `class_position`, not a separate known flag.
- **The recurrence seam.** `Context.Recurrence` returns an item's recurrence count; nil means none. The caller composes it, and this package never reads the ledger: `rankinputs.Load` (every consumer's loader since P2; the verb's own code under P1) reads `.evolve/recurrence-ledger.json` with `recurrence.ReadSnapshot` into `Inputs.Recurrence`, which is `recurrence.Ledger.ItemCounts()`, the recurrence package's own projection (an item's count is the largest non-generic entry whose pattern equals the item's id, since an autofiled recurrence item is filed under its pattern, or whose `fix_item_id` names it; [internal-recurrence.md](internal-recurrence.md)); `Inputs.Order` looks each item's id up in it. The snapshot read takes no lock, because the ledger is replaced by atomic rename and a lock would create a sidecar file.
- **`Inputs` is a consumer's whole input.** `Inputs{Config, Now, Recurrence}` holds the policy block, the clock and the recurrence counts by item id; `Inputs.Order(items, queue)` is `Order(items, Config, Context{Now, Queue: queue, Recurrence: by id})`, so a consumer passes the list it ranks and the whole pending queue `unblocks` walks, and composes nothing else (`TestInputs_OrderIsOrderOverTheWholeQueueWithTheRecurrenceCounts`). The map, not a function, makes the inputs plain data a loader can build in one place.
- **Run the order once, then look it up.** `Sequence(ranked)` returns an ordering function that sorts any subset of items by their place in one precomputed `Order` result, keyed by `inboxbatch.ItemKey` (`Item.Key()`, the id and the path) so same-id items keep distinct places, with an item the rank never saw after every ranked one, stably. It is what a consumer injects as `inboxbatch.Config.Order`, so `Classify` reuses one scoring run instead of scoring per cluster (`TestSequence_OrdersAnySubsetByTheRankAndKeepsUnrankedItemsLast`, `TestSequence_KeepsSameIDItemsApartByPath`).
- **The menu explains itself.** An item's top factor is the term with the largest contribution, the earlier factor in score order on a tie (the unexported `Breakdown.topFactor`, pinned through `Labels` by `TestLabels_NameTheLargestContributionAndTheEarlierFactorOnATie`; it was exported until the engineering-craft audit found no caller outside the package, and a breakdown always carries all six terms, so it guards no empty case). `Labels(ranked)` maps an item to `score 0.4475, top factor base` (`%.4f`, the precision the verb's table prints) and an item the rank never saw to `not ranked` (`TestLabels_ShowEachRankedItemsScoreAndTopFactor`); the triage prompt and `evolve inbox batches` print it on each item's sub-line.
- **One `scorer` per call.** `Score` and `Order` both build a `scorer` (the reverse-deps index and the recurrence seam) and score through it, so `Order`'s breakdown for an item is exactly what `Score` returns for it.
- **Unknown classes are named, not hidden.** `ClassWarnings` lists every item whose `priority_class` the order lacks, with `inboxbatch.CheckPriorityClass`'s message, the same rule `evolve inbox add` refuses with. The item still ranks, below every known class.
- **Every autofiled item carries a class** (since the plan's P2 prerequisite, 2026-10-06). P1 found eight production autofilers writing pending items without `priority_class`, which under P2 would have scored a class feature of 0 and sunk below mid-weight items. Each now stamps the class of the finding it files (correctness for a red CI run, a demoted contract gate, a fail-learning defect and a suspect triage-cap gate; stability for fleet starvation, a goal stall and an ADR-0072 halt; debuggability for an unexplained outcome), and cmd/evolve's `TestInboxWriters_EveryAutofiledItemCarriesAKnownClass` holds them to the checked-in `class_order`, with a source scan that reds on any unenrolled production write into `.evolve/inbox/` (ADR-0121 amendment; [the plan](../../plans/inbox-prioritization-2026-10.md)).

## Invariants

- **The contributions add up to the score, exactly.** Each contribution is `float64(value × weight)`: the explicit conversion forbids the compiler from fusing the product into the following addition (Go may emit a fused multiply-add on arm64), so the score is the plain sum of the rounded contributions on every architecture. Pinned by `TestScore_ContributionsAddUpToTheScore` and, through the verb, `TestCmd_InboxRank_ExplainContributionsAddUpToTheScore`.
- **The order is total and independent of input order.** Score descending, then a declared fix surface first, then the older filing date (undated last), then the id, then the file name. `TestOrder_TiesBreakOnDeclaredSurfaceThenTheOlderFilingThenTheID` runs all 720 orderings of six tied items; `TestOrder_IsStableAcrossRunsAndInputOrder` shuffles thirty items fifty times; `TestOrder_ASharedIDFallsBackToThePath` pins the last key.
- **Every feature is in [0, 1].** A weight outside [0, 1] is clamped, counts beyond a cap saturate and a negative count is 0. Pinned by `TestScore_NormalizesEveryFeatureIntoTheUnitInterval` and `TestScore_ANegativeRecurrenceCountIsNoRecurrence`.
- **Recurrence moves the rank and writes nothing.** Pinned at the verb by `TestCmd_InboxRank_ARecurrenceCountMovesTheRankWithoutWritingAnyFile`, which compares every file under the root before and after.
- **The order changes only on purpose.** `TestOrder_PinsTheSnapshotOrder` ranks a fixed projection of the 241 items pending on 2026-10-06 (`testdata/inbox-snapshot-2026-10-06.jsonl`: each item's id, weight, class, campaign, deps, filing date and files, with its file name) at 2026-10-06T00:00Z under the compiled default, and compares `rank score id` lines with `testdata/order-2026-10-06.golden`. A change to a feature, a factor default or a tie-break shows up as a diff of that file; regenerate it with `go test ./internal/inboxrank -run TestOrder_PinsTheSnapshotOrder -update` and review the diff. `TestOrder_SpreadsTheSnapshotsWeightTies` requires the 33 items tied at weight 0.5 to spread.

- **No other code orders inbox items by weight.** `TestNoProductionCodeOrdersByWeightOutsideTheRank` (`weightsort_ban_test.go`) parses every production `.go` file of the module (not `_test.go`, `testdata`, `vendor`, `acs` or hidden directories, and not this package's own files) and fails on any function that orders by a weight: a `sort.Slice`/`SliceStable`/`Sort`/`Stable` or `slices.SortFunc`/`SortStableFunc`/`MaxFunc`/`MinFunc`/`IsSortedFunc`/`BinarySearchFunc` call whose comparator names a weight, a `cmp` comparison or an ordering operator (`<`, `>`, `<=`, `>=`) between two weight-named operands (`Weight`, `weight`, `weightA`), or a `Less` method that reads one. It allows a weight compared with a floor or a literal, which is validation (`goalstall`'s and `starvation`'s weight floors, `lifecycle/file.go`'s (0, 1] check). `TestWeightOrderingSites_FindEveryShapeOfAWeightSortAndNoValidation` pins each shape on a fixture. On the pre-P2 tree (2026-10-06, `2f2cefdeb`) it names exactly the five old orderings: `inboxbatch` `Classify`, `weightOrder` and `weightDescThenID`, `triagecap` `RankForDispatch`, and the dashboard's `readQueue`. A weight that is not an inbox item's is named for what it weighs, so it never trips the guard.
- **The guard runs at every lane ship.** It reads the whole module, so `./internal/inboxrank/...` is in `repocontract.Packages()`, the ship-time repo-contract pack: a lane that adds a weight sort anywhere is refused at its own ship instead of reddening main. The package's tests are pure and fast, so the pack pays little for it.

## Findings

- **Why a snapshot, not the live inbox.** A golden over the tracked `.evolve/inbox` would change with every lane ship (each consumes an item) and every filing, so it would red main between landings (the whole-tree-test class of ADR-0110). The snapshot pins the function; the live order is one command away.
- **Wired on the live plane** (P2, 2026-10-06): on the runtime plane's 232 pending items (49 lane-ready), `evolve inbox rank --top 20` and the wave seed's first 20 are the same items in the same order, and the batches menu holds all 49 in rank order, each cluster placed by its best member. 45 of the 49 lane-ready items moved against the old weight order. The recurrence factor moved nothing: the plane has no `recurrence-ledger.json` yet.
- **The first order** (2026-10-06, the preview report, with the operator's corrected class order: correctness first, security last): 52 of the 55 lane-ready items move. Today's top ten held eight hygiene items; the new top ten holds nine stability items and one debuggability item, and the one lane-ready security item falls from 35th to 52nd. The largest fallers are hygiene items that describe silent failures, which is a labelling question (the operator's answer: re-class through the P3 judge or `evolve inbox edit --reason`, never automatically) rather than a factor question.
