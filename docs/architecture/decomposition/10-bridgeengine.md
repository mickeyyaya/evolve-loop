## 1. Context

`(*Engine).Launch` (engine.go:513-668) is the in-process `core.Bridge` entry every phase dispatch reaches: the production Adapter builds a FRESH engine per call (adapters/bridge/bridge.go:251-258 `gobridge.NewEngine(deps).Launch`), the subagent runner (internal/subagent/validateprofile.go:366) and the models-live probe (cmd/evolve/cmd_models_live.go:176) call it directly. In 156 lines it validates four required fields (:514-523), materializes the prompt and log paths (:524-542), serializes the request to argv (`launchArgs` :428-497) and runs `LaunchArgs` (launch.go:29-252) on a per-call `Deps` copy (:549-576 — the race-freedom contract, engine_concurrent_launch_test.go:26), records the attempt to `llm-calls.ndjson` (:582 → attempt_telemetry.go:74-137), clears or records boot strikes (:585-589, :647-651), reads the artifact on exit 0 (:590-603), persists the launch stderr (:612-614) and then CLASSIFIES the exit (:615-667): `"bridge: launch exit=%d"` + the mined cause, wrapped with `core.ErrArtifactTimeout` on 81 (:636-638), `core.ErrTransientBridgeFailure` on 80/85/86/124 (:646-653) and on -1 under a cancelled context (:664-666), plain otherwise (:667 — 127 deliberately plain, :643-645).

That classification is the component's real failure surface and the one thing a triage reads — and it produced NO signal. A launch death reached `signals.ndjson` only as the orchestrator's `phase.outcome` / `phase.aborted` (internal/core/signal.go:75-91: verdict, archetype, duration_ms — no exit code, no CLI, no cause, no bridge origin). The bridge module's four producers (signal.go:1-9: `NewEngine` :395-399, `attemptLogContext.warn`/`.tripwire` attempt_telemetry.go:54-65, `paneLivenessHandler` signal.go:66-80) covered token telemetry and pane liveness, never the exit. The design promised a `BRIDGE_EXIT_*` projection (signal-center-design.md:231-232) that was never built (grep `BRIDGE_EXIT` over go/: zero hits).

The same belief was spelled twice: `Launch`'s sentinel table (:636-667) and `modelAttemptCause` (attempt_telemetry.go:227-260 — the `llm-calls.ndjson` `CauseCode`, :131) were two `switch`es over one exit vocabulary; the exit-81 sub-cause was derived from the same stderr twice (:625-629 vs :262-280). The vocabulary the parser accepted (:273-277) was spelled on the emitter side (driver_tmux_wait_diagnostic.go:11-20) and the marker it keyed on (stopreview.go:101) was re-spelled at :710. Two hand-written `[engine]` stderr lines (:587, :649) swallowed store errors with no test (grep over `*_test.go`: zero hits); two silent sites (`_ = os.WriteFile` :613 — the forensic launch-error file cycle-270 needed, :604-611; `err == nil` on the artifact read :599 — a PASS with an empty `Stdout`) produced no bytes at all. No test pinned the four required-field strings (engine_launch_test.go:51-58 asserted only `err != nil`), the `Completion == "stdout"` read path (:596-598), `ClearBootStrike` on a non-80 exit (:585-589), exits 85/86 through `Launch`, the 300-rune cap (:731-737), or the full argv vector (`--secondary-artifacts=` :440-442 was emitted by no test).

// Outcome is what one launch exit MEANS — the value object the error chain, the attempt ledger and the
// signal stream all read from. Zero value = ExitOK. (No Name / Cause fields: neither is read in
// production — the name is the table's, the cause only feeds Err.)
type Outcome struct {
    ExitCode     int
    CauseCode    string // the llm-calls.ndjson cause_code — "driver_error" for -1 AND unknown (the ledger never changes)
